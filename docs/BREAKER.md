# 分类熔断与恢复

Papa 的自动熔断和恢复以整站为单位。阶段、类别和指纹用于定位故障；某阶段成功只记为局部证据，不能独立解除整站保护。统计已经落库的终态任务轮次，HTTP 请求的限流反馈另外交给请求治理器处理。一个任务内部重试多次不增加多份失败；同一任务轮次重复通知去重，成功不抵消失败数。

## 三条保护线

- 短窗口内，同阶段、同类别和指纹的不同任务达到 `fast_threshold`，立即暂停整站，并在报告中注明触发阶段。
- 短窗口混合错误达到 `mixed_threshold`，先进入整站受限观察。最后一次失败后完整 `observe_for` 内没有新增失败，且所有已注册阶段完成三次本轮受控任务验证，则等全站在途任务结束后确认恢复。优先验证本次失败任务：同阶段至少三个不同失败任务时选三个；只有一两个时轮换这些样本完成三个独立执行轮次，重复通知不计数。没有失败样本的阶段仍需三个不同真实任务，空闲不默认正常。未执行过的阶段也必须验证。尚有失败样本待验证时保留串行验证机会，受样本和整轮截止时间约束；没有可继续的样本且全阶段证据不足时暂停整站并逐阶段试探；报告时间线或展示样本截断不影响完整的运行验证证据。新增失败重新开始观察计时，但不延长总恢复预算；达到快速线或硬线会提前暂停。
- 原 `window` / `threshold` 仍是整站失败总数硬上限，不因错误类型分散或夹杂成功而豁免。检测记录容量不足也进入保护，不能悄悄丢弃失败后低估风险。

参数与默认值见 [CORE_CONFIG](CORE_CONFIG.md)。稳定错误码使用 `papa.WithFailureCode(err, phase, code)`；不要把任务 ID、URL、时间戳拼进 code。框架依次参考稳定业务码、类型化 HTTP/网络错误及归一化文本；HTTP 状态码仍参与指纹，不会把 403 与 429 当作同一错误。

## 限流

发现 429 或明确的 Retry-After 后，检查现有请求治理和 AutoThrottle 的有效开关；两者开启才调整自动间隔，不偷偷打开开关。合法 Retry-After 的等待期限独立遵守；没有有效头且自动降频关闭时沿用固定间隔/重试。限流反馈不直接冒充终态失败，探针也不进入普通任务失败数。

## 只读探针

`App.Run` 在提交入口及恢复队列之前恢复事件并启动管理循环。直接组装 `Engine` 的宿主需先调用 `InitBreakerRuntime(ctx)`，失败应停止启动，再调用 `ApplyRegisterStage`。

业务在 Run 之前注册通用公开接口：

```go
app.Engine.SetBreakerProbe("synthetic", "detail", func(ctx context.Context, req papa.BreakerProbeRequest) (papa.BreakerProbeResult, error) {
    // 用受治理的请求 API 和 ctx 做只读校验；验证发生错误的操作。
    // 混合错误应逐组检查 req.Evidence，不能只验证首页可访问。
    healthy, err := checkDetailReadOnly(ctx, req)
    return papa.BreakerProbeResult{Healthy: healthy, Semantic: healthy, Detail: "指定样本 detail 语义检查", SampleID: req.SampleID}, err
})
```

空 stage 注册站点兜底探针：框架对每个阶段分别调用，回调必须根据 `req.Stage` 检查该阶段语义，不能把一次首页 HTTP 200 当作全部阶段通过。已注册的专用阶段探针优先。回调必须只读、尊重 context，不调用完整 Fetcher、不写业务数据、不派发子任务、不下载产物。回调是可信扩展，框架不能沙箱阻止自定义代码写库。缺少探针或只有 HTTP 200 的阶段不能默认通过。

冷却到期后先等暂停前在途任务结束，再保存整站探测轮次预算，逐阶段执行只读探针，每站同时最多一个。`max_probes` 限制整站探测轮数，每轮包含全部阶段；某阶段失败则整站回冷却，下轮全部重新验证。阶段间遵守 `interval`，每个阶段开始前保存记录。一个阶段通过不会解除暂停。

全部阶段探针通过后保存 `ramping`，才允许整站限量真实任务。默认每个阶段至少一个本轮任务成功；混合错误事件要求三次失败样本验证。仅显式声明完整只读覆盖的阶段可用完整只读证明替代，默认两次、混合错误三次，规则见下文。全部阶段满足条件、经过 `ramp_for` 后，停止新增放行并等待全站在途任务结束，才能确认 `recovered`、清空整站运行计数。报告保留清零前统计、原始失败证据和清零时间；最终报告保存确认前不全量放行。未满足验证条件的阶段保持未验证，总恢复预算耗尽则保持保护并安排一小时后复查。这里的真实任务不特指 recover 队列，也不是另造的测试任务。任何阶段晚返回失败都会取消本轮恢复；此前阶段成功只保留在报告中。

次数、总时间预算耗尽或探针超时转 `manual`，保留保护并保存下一次小时复查时间。`manual` 是等待复查/人工处理，不是事件结案；只有 recovered / closed 才设置结案时间。回调仍未退出时每小时记录跳过原因，不能堆积新的探针；Stop 不会宣称已排空。

人工暂停只在本次进程运行期间有效，重启不恢复。人工暂停完全覆盖自动保护范围时，结束该自动事件并保留历史报告；若只暂停其中一个阶段，则两种暂停分别生效。人工解除是操作员干预，不证明所有阶段正常，因此不清空计数；报告记录人工操作，不能显示成自动验证恢复。自动恢复只解除自己的暂停，不能解除仍在本进程生效的人工暂停。`manual` 表示自动探测预算耗尽等原因造成的“自动保护等待小时复查或人工处理”，仍需跨重启恢复。

## 持久化与报告

升级先显式执行宿主迁移入口，创建 `crawler_breaker_incidents` 与追加历史表 `crawler_breaker_history`；正常启动不迁移。初始化读不到事件表会停止启动。每站最多一个活动事件，报告包含触发失败数、窗口失败/成功数、分类指纹、证据、状态时间线、探测次数、冷却期限、假设、反证、缺失信息及最终结论。后台原有熔断分析入口提供查询和文本/JSON 导出。

报告按修订号保存，每次保存快照分配新修订，避免数据库已提交但确认丢失后，窗口自然过期造成同修订内容冲突。管理检查与报告写入分别通过 `select + timer` 驱动：管理每 200ms 检查一次；正常写入结束后等待 200ms 合并新证据，失败后等待 1s 再试，单批写入 context 限时 2s。持续任务流不会反复推迟写入定时器，写库等待也不阻塞恢复期限检查。探测、解除暂停及全量恢复必须等对应控制状态保存；仅仅追加更新证据不重新锁住已保存的状态。

正常停机在 worker/探针退出后补写最后状态，失败则报告未排空。强杀仍可能丢失最后一个未刷写周期，写入故障时窗口可能更长；任务终态与事件写入不具有跨表事务原子性。重启先恢复已持久化的保护和预算，进行中的探测/限量恢复回到冷却，不信任中断的在途任务已经证明恢复；`manual` 保持暂停。事件记录过的 Retry-After 会恢复到治理器，普通请求也不能提前绕过。已建立熔断事件的精确失败轮次、原始时间和容量保护单独保存在控制快照中，重启恢复 Detector，不能在验证前直接清零；窗口自然过期仍按原时间发生。强制解除或人工结束事件后，启动读取该站最新快照以保留尚未过期的失败。成功验证证明不跨重启复用。旧版本快照没有精确窗口时保留已知失败下界并转人工，报告说明缺失原因；人工重试重新验证全部阶段。首次形成事件之前的内存窗口仍不单独持久化。

此版统一整站保护，不增加路由或账号调度器。账号、代理、迁移和网络问题由分类报告提出验证方向；不凭一个 404、选择器错误或请求超时宣布整个网站宕机，不自动猜测新 URL 或修复选择器。业务需要根据受控探针结果决定如何处置；没有证据时明确报告“无法确认”。

## 接口与数据源收敛

已移除 `Engine.BreakerIncidents` 和 `MonitorConfig.BreakerIncidents`；宿主统一使用 `BreakerReports(ctx, site)` / `MonitorConfig.BreakerReports`。后台、事件流和持久报告共用一个事件 ID。Detector 是唯一终态计数和触发证据来源；不再运行旧桶计数器、旧内存历史列表或后台兼容回退。obs 日报查询当天追加历史及日初仍在保护的最后状态，包括当天没有新日志的持续故障。最多展示10000条；截断时明确报告截止状态无法确认，不用前缀中的最后状态冒充当天最终结论。离线时按最后出现保留最多 100 个事件引用并说明截断，不再从任务日志拼造第二份报告。

复查中的阶段隔离、在途恢复任务、报告更新阻塞恢复期限、混合观察固定转暂停四项已修正，验证说明见 [施工与验收](issues/2026-11-12-breaker-implementation.md)。

## 运营查看运行过程

同一事件的报告包含全阶段待验证/试探中/通过/失败进度、本轮真实任务成功数、每轮暂停冷却和重试计划，以及恢复清零时间。时间线记录整站状态变化和阶段里程碑，不逐条复制全部成功日志。后台弹窗每 3s 更新，保持当前选中的历史事件，关闭后停止请求。后台文本和 JSON 导出展示当前 Lifecycle；obs 日报读取同一运行过程产生的追加记录，按当天起止时间查询；`breaker_transition` 事件让只观察后自行恢复的事件也能进入 obs，而不只关注首次熔断。

阶段清单上限 128，当前弹窗时间线 128 条、错误样本 256 条；超限显式标记，阶段清单不完整时拒绝自动恢复。128 条只限制当前展示，不删除已保存的追加历史；完整历史可从框架数据「熔断运行历史」按事件 ID 查询。重启清除旧阶段验证通过标记，当前全部阶段重新验证，既有时间线和剩余预算保留。

## 重试恢复与强制解除

- `Engine.ResumeSite(site)` / `ResumeCrawling()`：活动自动事件重新获得一轮有界恢复预算，保留失败数、整站保护和历史，所有阶段重新验证；成功保存控制状态后才开始试探。仍在运行或尚未退出的探针不接受重复重试。纯人工暂停可以直接解除。同一进程内人工接管过自动事件，再普通恢复时仍须重新验证。
- `Engine.ForceResumeSite(site)`：明确跳过自动健康验证，关闭事件并解除该站暂停。保留失败窗口，下一次失败可能立即再次保护；报告标记人工强制解除，不能显示为健康恢复。
- 后台普通按钮为「重试恢复」，请求 `POST /api/breaker/resume`；「强制解除保护」使用独立的 `POST /api/breaker/force-resume`，必须指定一个站点，不接受全部站点或单阶段范围，确认后执行并单独记操作日志。

人工接管标记和人工暂停仅属于本次进程；重启不恢复人工暂停。自动事件的 `manual` 状态仍跨重启保护。普通重试会重新授予预算，单纯重启不会延长预算。总超时、人工结束等中止路径会将正在试探或尚未开始的阶段标记为「验证已中断」，记录结束时间和原因；晚结果不能改回成功。

## 控制与报告的边界

运行使用原始站点/阶段标识、完整的验证状态和 Detector 证据；报告是只读投影。脱敏、展示截断和时间线容量不会回写控制字段。当前控制、失败窗口与报告仍放在 `crawler_breaker_incidents.payload`；新增 `crawler_breaker_history` 只追加当时的运行记录，两者同事务保存。完整快照上限 16 MiB，超过上限写入失败并保持保护，不裁掉失败窗口假装成功。本次升级需要显式迁移以创建追加历史表。新版本可读旧快照，旧二进制不能直接读取新快照；回退需使用升级前备份或配套转换。

## 空闲阶段的完整只读验证

默认行为仍是「语义探针 + 本轮真实任务成功」。队列为空不代表正常，普通探针成功也不能代替真实任务；没有任务的阶段保持未验证，耗尽总预算后转人工。不会自动重投已完成任务。

只有阶段的**全部操作都能由只读检查覆盖**，才可在 `papa.StageSpec.BreakerReadOnlyCoverage`（直接使用 Engine 时为 `StageConfig` 的同名字段）填写完整覆盖范围。空串为默认；纯空白或超过 1024 字节会在注册阶段报错。不增加 YAML 开关，现有业务不会自动启用。

设置该字段是业务对完整性的明确承诺：探针必须使用有效样本，复用真实阶段的读取、解析和必要字段校验，覆盖阶段涉及的各种必要路径。只检查 HTTP 200、首页或某个字段都不合格。包含写库、下载、派发等操作的阶段，纯只读探针无法完整证明其健康，必须保持字段为空并等待真实任务。

继续使用已有 `SetBreakerProbe(site, stage, callback)`，没有新队列或管理器。对于显式声明的阶段：

1. `req.Coverage` 带入声明范围，`req.Pass` 是本轮检查序号（默认两次，混合错误三次）。每次都须重新读取并独立验证，不能直接返回第一次缓存的成功；有多个代表性样本时应使用不同样本，不能挑选容易成功的页面绕过故障。
2. 每次结果都必须满足 `Healthy && Semantic && Complete`，且 `Detail` 非空。`Complete` 表示本次确实检查了**整个声明范围**，`Detail` 写明实际检查的范围、样本标识及结果，不写密钥。没有有效样本、只能检查部分路径时返回 `Complete: false`，说明缺失部分。
3. 各次调用间隔至少既有 `interval`；启动检查前遵守 Retry-After，回调仍应使用现有治理请求链路。探针超时和总恢复期限继续生效。任一次失败或不完整都不能通过；重试从所有阶段的第 1 次重新开始。`max_probes` 仍按整站轮次计算。
4. 未声明阶段，即使返回 `Complete: true`，仍须真实任务成功。所有阶段各自满足条件、整站观察期结束、在途任务排空并保存结果后，才统一清零并恢复。验证期间真实任务失败仍取消恢复。重启后既有只读证明全部作废，按当前声明重新验证。

例如，一个只做读取和解析、没有副作用的阶段可以声明 `BreakerReadOnlyCoverage: "目录及详情读取、全部解析路径、标识与必填字段校验；无写入、下载、派发"`。它的回调必须实际完成这些检查后才返回 `papa.BreakerProbeResult{Healthy: true, Semantic: true, Complete: true, Detail: "本次样本及逐项校验结果"}`；这段结果结构不是默认成功模板。

报告为每阶段记录 `verification`（`task` / `readonly`）、`coverage`、`probe_successes`、`task_successes`，并生成 `verified` 与 `verification_note`。文本、JSON、后台和 obs 使用同一投影，分别展示检查进度与验证结论；普通探针 `passed` 而真实任务为零仍显示「未验证」。阶段局部通过不代表整站已恢复，整站结论仍以事件状态为准。混合错误观察直接通过真实任务恢复时，报告标记真实任务验证，不冒充执行过只读验证。

多次检查降低偶发成功的影响，**不能证明业务探针没有漏测**。框架强制声明、次数、间隔和结果条件，但无法推断任意业务代码是否覆盖完整。维护有效样本和真实校验逻辑仍是业务责任；无法完整覆盖的阶段只能等待真实任务或由运营明确强制解除，强制解除不会记成健康恢复。


## 混合错误的指定失败样本

混合错误事件在开始验证时固定每阶段最多三个不同失败任务身份，重试/轮询次数不构成新身份。原失败窗口自然过期不降低取样门槛；重启保留目标身份，但清除成功证明。选中的任务优先通过现有版本化重试、任务认领和幂等流程执行，框架不直接调用 Fetcher。正在执行、已经排队、人工/永久禁止补偿、尚未到可重试时间的任务不会绕过原规则；无法重试的原因进入报告。

只读探针请求增加 `Sample` 和 `SampleID`。存在指定失败样本时必须实际检查该任务对应页面，成功结果的 `SampleID` 必须回传相同值；只返回首页成功或者忽略样本 ID 不通过。`Sample.URL` 是脱敏线索，必要时按任务 ID 获取业务自己的有效目标。三个样本时按 A/B/C 检查；两个时 A/B/A；一个时 A/A/A，每次独立请求且间隔 `interval`。没有失败样本的阶段由业务提供有效代表性样本，不能用空队列代替验证。

混合错误的三次语义探针并不豁免真实任务验证；只有声明完整只读覆盖的阶段可替代。普通阶段仍需对应失败样本的三次真实任务成功，没有本次失败样本则需三个不同任务。单个阶段通过不能解除整站保护。报告直接使用控制侧验证结论，不用原始成功通知数推断健康。

## 每小时复查与每日历史

一轮恢复耗尽预算后继续保护，一小时后再进行一轮有界复查；每轮重新授予既有 `max_probes` / `max_recovery`，清除旧证明，保留失败证据。每小时复查满足全部阶段、观察期、在途排空和持久化门槛后自动恢复。人工暂停不自动解除；未退出的探针不重叠，记录本次跳过原因。Retry-After 更晚时继续等待。重启保留已保存的下次复查时间，错过多小时只启动一轮，不补发积压检查。小时周期固定，不增加新的配置开关。

每次暂停、验证、重试、正常停止、中断发现、重启和恢复都追加持久记录，保存当时的验证方式、范围、样本及结果。重启或修改声明不覆盖旧记录。非正常中断在下次启动时记录发现时间，明确标注确切中断时间未知。旧版本已有事件在升级后写入历史起点，不能补造升级前已经丢失的过程。

obs 使用自身当天的起止时间查询：展示日初仍在保护的基线和当天变化，回查昨天不混入今天的恢复结果。一天没有新动作时仍显示持续保护。单次日报最多展示 10000 条，超过时明确提示，数据库记录保留；后台框架数据提供只读历史查询。记录按事件内序号幂等保存，保存确认丢失不会重复追加。未保存积压最多 4096 条，超过后保护站点并标记记录可能不完整，不继续清零恢复；正常保存后清理内存待写记录。

## 串行样本和超时

同一站点的观察、低速恢复和只读验证都串行执行，跨阶段也只有一个验证样本。不同站点互不串行。失败样本先选中并保存身份、截止时间，正常调度和验证重投统一经过同一准入检查；正常队列已能执行选中任务时直接使用该轮，不再额外重跑。已完成本次要求的样本不会重复投递。`ramp_concurrency` 保留为旧配置兼容项，不再增加验证并发。

真实样本从选中起最多10分钟，包含排队、账号/资源配额等待及 handler 执行；`max_recovery` 的整轮截止更早时先结束本轮，默认5分钟预算不会自动延长。只读样本同样受选中后10分钟上限约束，原 `probe_timeout` 更短时优先生效。等待时间与样本身份保存在控制快照中，重启不会为同一等待重新计时；旧执行成绩全部作废。

A 超时后记为未通过并取消 context。A 尚未退出时不执行 B，不再重投 A，也不启动新的小时复查；obs 记录占用原因。A 退出后可串行检查剩余 B/C，但它们成功不能替代 A，本周期不能自动恢复；下一周期重新验证。若业务忽略取消后最终完成，保存实际任务终态以免丢失业务执行结果，但该迟到结果不计健康证明。Fetcher 必须将收到的 context 传给请求、下载及等待操作。

旧控制格式升级时补齐混合错误的三次验证要求；无法排除曾由混合错误升级为硬保护的旧事件也保守使用三次验证。只在升级入口转换，运行时仍以控制状态为准。完整过程继续追加保存，包含选中、超时、执行退出、重启中断和小时复查；不会覆盖此前日期的历史。

样本取消后的错误按错误链区分：仅包含 `context.Canceled` / `context.DeadlineExceeded`（包括包装）的错误属于取消，不增加业务失败数；独立业务错误，以及同时包含取消和业务错误的组合错误，限时保存失败终态并追加迟到结果和实际错误，照常计数。失败落库/通知结束前不释放串行位置。完成时间或终态无法确认时保留未结算责任，不把真实错误退回为普通取消。


### 串行样本的未结算失败

真实业务失败在写任务终态前，先把任务 ID、repeat/reprocess 轮次、原错误类别/指纹、补偿条件和原样本截止时间保存到现有 Recovery 快照。任务失败终态未确认，或确认后的计数快照尚未保存，都不允许放行后续验证；恢复队列、错误队列、轮询与人工重投也不能替换待结算轮次。超时、每小时复查和人工重试不能清掉这份责任。

原 handler 及收尾退出后，由现有报告定时循环接续结算，不调用 FetchHandler。结算失败每分钟再试，原执行轮次不变；终态 UPDATE 仍以 processing + repeat/reprocess 为条件，回执丢失时查询同一轮终态，避免重复追加 error 或推进补偿版本。失败计数和清除待确认结果一起写回恢复快照，历史与快照同事务提交；重启只重新确认落库，不重新执行业务，不复用成功证明或延长十分钟截止时间。原失败已超过统计窗口时，保留结算历史，不把旧错误重新塞入当前窗口。

obs 追加 failure_pending、failure_settlement_retry、failure_settlement_wait、failure_settlement_restart、failure_settled；记录任务与轮次、真实错误、等待原因及结算结果。迟到结果不能成为验证成功，人工暂停仍然有效。数据库行被删除或轮次改变时，无法确认原结果，继续保护并在记录中说明冲突，不覆盖新轮次。

不新增表、控制器、队列或独立调度循环。跨重启保留以待确认快照已提交为前提：如果数据库连这份快照也无法保存，运行中仍阻止放行并重试，但此时强杀进程无法保证恢复尚未持久化的错误原文；停止流程会报告状态保存失败。关闭熔断配置不允许越过已持久化的待结算失败；须重新启用后继续结算。


2026-11-13 收紧：串行样本已确定终态失败时，在完成时间、账号反馈、trace/归档等辅助收尾之前保存 PendingFailure。覆盖不可重试错误、重试耗尽、明确补偿/账号失败、取消后真实错误和 panic；仍有重试机会的普通错误不提前形成终态。待确认结果存在时，取消回退不能把原 processing 行重置成 pending。结算旧结果前先推进统计器到当前时间，不依赖访问后台或重启来清理过期窗口。

后台结算只追加真实失败与 failure_settled 历史，不再发出第二次 task_failed 执行事件。执行事件是过程观测，进程中断可能使其不完整；待结算结果、任务终态和事务内追加的熔断历史是失败结算依据，不能把补记结算当作又执行了一次任务。

辅助收尾再次报错或 panic 不替换已保存的业务失败：原 worker 和重启结算使用同一份 PendingFailure 生成终态字段、失败分类和报告证据；收尾异常仍按原异常路径上报。
