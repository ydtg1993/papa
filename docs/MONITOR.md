# Papa 监控服务后台手册

> 面向：按采集任务流、运行监控与报告、数据与资源、系统管理四类使用 OA 后台。
> 配置项见 [CORE_CONFIG.md](./CORE_CONFIG.md) 的 `server` 段。

页面归档下载用打开的根目录句柄约束实际读取，拒绝最终文件或父目录链接逃逸、拒绝非常规文件；根内合法文件仍可下载。归档根目录由宿主可信配置，浏览器仅提交相对路径，不是通用文件下载服务。日志与报告的已知凭据遮盖、原始证据边界见 [OBSERVABILITY.md](./OBSERVABILITY.md)「诊断输出的脱敏边界」。

---

## 0. 一句话

框架内置一个 HTTP 监控后台（`server.enabled: true`），访问 `http://localhost:<port>/monitor`。一级导航固定四类，只展示当前类别的二级入口；默认打开「运行监控与报告 → 运行概览」。

| 一级入口 | 二级内容 |
| --- | --- |
| 采集任务流 | 业务采集方案/工作台（注册后显示）、周期批次、规则与发布、Agent 候选、异常处理 |
| 运行监控与报告 | 运行概览、运行质量、运行报告、运行日志 |
| 数据与资源 | 采集任务 `crawler_tasks` 的手动操作，行内「追踪」弹窗查看执行记录；业务自行注册专门页面 |
| 系统管理 | 系统设置（包括业务注册的模型设置）、访问令牌、操作日志（注册后显示） |

跨分类的详情入口自动同步类别、二级选中项与标题；未保存页面仍可阻止离开。站点筛选只在支持站点范围的页面显示；全局队列、运行报告/日志和系统管理不显示站点筛选。手机通过「菜单」展开四类，选中后收起，Esc 关闭并返回菜单按钮。这里的「任务流」是操作导航，不是新增 DAG 调度器。

> **单实例边界**：阶段概览读取当前运行进程内存，任务数据读取数据库；单独启动的管理台不拥有另一个进程的 Worker 快照。Papa 不支持多实例协同部署。

> **实时看板 ≠ 事后报告**：本后台回答「现在队列 / worker / 暂停是什么状态」；「这一轮跑得怎么样、
> 失败怎么分组、退出后总结」由 `obs` 事件流 + `papa report` 产出（`report.md` / `report.json` /
> `ai-brief.md` / `ai-brief.json`），见 [OBSERVABILITY.md](./OBSERVABILITY.md)。

## 1. 鉴权（访问令牌 + 白名单）

所有 `/api/` 接口都过两道校验：

1. **IP/CIDR 白名单**（存在 `crawler_config` 表的 `cfg_key = ip_whitelist` 行，运行期在设置页改；**不在 config.yaml 里**）。本进程对白名单读取有 **5 分钟 TTL 缓存**：后台保存即时生效；跨实例/直接改 SQL 的变更由 30 秒重载循环检查，最迟约 5 分钟可见（`CachedStringListReader` 装饰器，见 `changes.md`）。
   语义：**行不存在 / 空数组 / 值解析不出来 → 不限制来源**；有值 → 只允许列出的那些来源。`/monitor` 页面本身只查这一道。
2. **访问令牌**：请求带 `Authorization: Bearer <令牌>`，或 `X-Auth-Key: <令牌>`。方案名按 RFC 7235 **大小写不敏感**（`bearer` / `BEARER` 也收）；令牌本身逐字节精确匹配，不做大小写归一。
   **不再支持 `?key=`**（凭据进 URL 会落进浏览器历史与访问日志）。
   **每次请求直接校验令牌哈希、启用状态和非空操作人**，不再以令牌数量决定是否允许匿名访问。计数缓存不参与授权；CLI 创建的第一把令牌、停用或删除在下一次查库校验时生效。

**哪些路径要过哪道门**（三类，别混）：

| 谁 | 白名单 | 令牌 |
| --- | --- | --- |
| 后台内置数据接口（`/api/*`，含 oao 表格 `/api/oao/*`、`/api/tokens/*`、`/api/pages`） | 要 | 要 |
| `/monitor` 这张 HTML 壳（还有 `/static/*`） | 页面要、静态资源不要 | **不要** —— 令牌是在页面里填的，填之前也得拿得到页面 |
| **挂在同一个 mux 上的业务路由**（`Router` 默认套的就是 `Monitor.Auth`） | 要 | **要，且不看路径前缀** —— 要公开就显式 `NoAuth()` |

第三行是 2026-10-13 修的：`Monitor.Auth` 以前复用的是内置端点那条"只看 `/api/` 前缀"的判断，
于是**注册在非 `/api/` 路径上的业务路由只剩白名单那一道**（白名单内的任何人都进得来）。见 `changes.md`。

`/api/*` 的响应一律带 `Cache-Control: no-store`：带凭据的数据（仪表盘、日志下载、白名单……）
不该被中间代理缓存 —— 否则令牌停用/删除之后，那份旧的 200 还能被重放出来。

### 令牌存在库里，一条属于一个操作人

凭据不再是配置里的单个 `auth_key`，而是 **`crawler_access_token`** 表里的多条令牌：

| 字段 | 说明 |
| --- | --- |
| `operator` | 令牌归属的人 —— 操作日志据此记「谁干的」 |
| `token_hash` | `sha256(令牌)`，唯一索引；**库里不存明文** |
| `enabled` | 停用而不删 |
| `note` | 备注（哪台机器/哪个人） |

**首次部署必须在服务器本机创建令牌**，不能匿名调用 HTTP 新增接口：

```sh
papa token add --operator 张三 --note "运维机" -c configs/config.yaml
```

明文只打印一次，请当场保存。已有有效令牌登录后，可在 **系统管理 → 访问令牌 → 新增令牌** 为其他操作人创建令牌；也可继续使用 CLI。

**管理令牌**：同一页可以看列表、**停用/启用**、**删除**（停用启用带状态条件，重复点击只有一次生效，
第二次会提示"该令牌状态已变，请刷新后重试"）。页面**不显示令牌本身**——库里只有哈希。

> **升级注意**：原先依赖空令牌表匿名访问的安装现在会返回 **401**。升级前先用 CLI 创建令牌；已存在的有效令牌无需轮换。本次不新增字段或迁移；首次安装仍需先运行 `papa migrate` 建表。

> **最后一条记录仍禁止通过后台删除**，保留既有误操作保护。即使外部清空令牌表也不会开启匿名访问；无可用令牌（空表或全部停用）时，使用服务器本机的 `papa token add` 恢复。

**几条要记住的行为**：

- 空令牌表、全部停用、缺少数据库/校验器、查库失败时，管理接口都拒绝访问；不因来源是本机或在 IP 白名单内而绕过。
- `/monitor` 和静态资源仍可加载登录界面。默认首帧下发 `data-auth-required="1"`；没有本地凭据时显示登录框。登录凭据由 localStorage（`papa_monitor_key`）保存，`localhost` 与 `127.0.0.1` 需各登录一次。
- 停用或删除正在使用的令牌，后续校验会返回 401、页面回到登录框。替换令牌时先创建新令牌，再停用旧令牌；已通过鉴权的在途请求不追溯撤销。
- 自定义 `MonitorConfig.VerifyToken` 是宿主明确提供的认证实现，必须自行验证身份；未注入时默认拒绝。`AuthRequired` 仅控制登录框展示，不能取消接口鉴权。显式 `NoAuth()` 路由属于宿主公开接口，不属于管理接口。
- IP 白名单是附加的来源限制，空白名单不等于匿名授权。本次不改变内网采集、目标网站登录会话或人工发布边界。

令牌页的写操作（新增/停用/启用/删除）和表格页的动作一样**记进操作日志**（开启 `server.operation_log` 时），
所以「谁给谁建了令牌、谁停用了谁」都查得到。审计里记的是操作人与备注，**不含明文令牌**。

队列治理面板的「立即执行」（`POST /api/{error,repeat}queue/process`）与右上角铃铛面板里的「恢复」
也**记进操作日志**（与令牌页同一处境：这三处是后台自带的原生接口、不走表格组件，但都会批量改数据 ——
审计不该因为"这不是表格动作"就断档）。审计行里：`table` = 队列名（`repeat_queue` / `error_queue`）
或 `breaker`，`action` = `process` / `resume`，`values.processed` = 实际处理条数，失败原因在 `error` 列。

> 写入是**异步**的（后台队列，不占业务响应）：写库失败、或队列堵了（写库跟不上）时，
> 那条记录会**落到日志文件**里（一行 JSON，可捞回来补录），既不丢审计也不反压业务。
> 关停时会先把队列排空再关数据库。

> 升级时表要自己建 —— 跑一次迁移（脚手架项目里 `make migrate` 与 `papa migrate` 等价，
> 独立使用 CLI 时运行 `papa migrate`，见 [CORE_CONFIG.md](./CORE_CONFIG.md) 第 2 节。
> 之后用 `papa token add` 给每个人建一把 —— 原来共用的 `auth_key` 请停用/删掉对应令牌。

## 2. 设置 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/settings` | 返回当前白名单（回显**原样**输入）、它持久化在哪（`whitelist_source`，空串 = 该宿主没接配置存储）、日志目录 |
| POST | `/api/settings/whitelist` | 更新白名单并交给宿主持久化（papa 落在 `crawler_config.ip_whitelist`），**成功即生效**；body `{"whitelist": ["127.0.0.1","10.0.0.0/8"]}`。写时严格：有条目不是 IP/CIDR 就整单 400 不落库；落库失败 500 且旧名单继续生效 |
| POST | `/api/settings/shutdown` | 触发优雅退出。**body 必须带 `{"token":"..."}`**（要求操作人重新输一遍自己的访问令牌），校验不过返回 403 且不关停；宿主没注入校验器时该接口返回 404 |

### 访问令牌 API（「访问令牌」页用）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/tokens` | 列表：`{"tokens":[{"id","operator","enabled","note","created_at","updated_at"}]}` —— **不含哈希与明文** |
| POST | `/api/tokens` | 新增：body `{"operator":"张三","note":"运维机"}` → `{"id":4,"token":"<明文，只此一次>"}`；操作人为空返回 400 |
| POST | `/api/tokens/enabled` | 停用/启用：body `{"id":4,"enabled":false}`；状态已被别人改过返回 409 |
| POST | `/api/tokens/remove` | 删除：body `{"id":4}`；不存在返回 404 |

这几条同样过白名单 + 令牌校验；出错回 `{"error":"..."}`，前端把这句话原样显示给用户。

## 3. 表格页（oao 组件）

后台的表格页由独立组件 [github.com/ydtg1993/oao](https://github.com/ydtg1993/oao) 渲染。
**组件是纯展示层，不碰数据层**：业务声明"显示什么、怎么显示"，并实现 `oao.Source` 提供数据。

> **例外**：「系统管理 → 访问令牌」操作页**不是**表格页。它要「新增」并把服务端生成的明文令牌交给操作人看一次，
> 而表格组件的动作只回 `{"status":"ok"}`、不回数据（组件不给"动作返回数据"这个口子）。
> 所以这一页是后台自带的原生模块：`/api/tokens` 三条接口 + `mo.js` 里自己渲染的表格，接口在 `admin/tokenadmin`。

> **表格归属**：任务操作表 `task`（对应 `crawler_tasks`）归「数据与资源」，Trace 合入任务行弹窗；操作日志 `operation_log` 归「系统管理」。业务表格只有显式 `UseTables` 注册后才出现，业务专门页面用 `UsePage` 注册；框架不扫描业务数据库。

### 任务操作与追踪

「数据与资源」默认只提供任务表一个入口，不展示整个系统数据库目录或独立站点快照。

| 入口 | 能力 |
| --- | --- |
| 采集任务（`crawler_tasks`） | 查询、站点/阶段/状态筛选、重新抓取（重投）、追踪、加急、开停轮询、调整周期、标记失败及删除 |
| 任务行「追踪」弹窗 | 自动按当前任务 ID 查询 `crawler_task_trace`，按尝试次数展示步骤、耗时、错误、采集数据与归档页面入口；执行证据只读 |

任务表复用现有 `task` 标识和 `/api/oao/task` API，因此旧的任务链接、追踪抽屉、动作审计以及版本号/任务状态/批次保护继续生效。界面中的「重投」就是重置并重新投递任务，不是直接改数据库状态。标记失败需要填写原因；处理中任务、周期控制与批次成员的可执行动作仍受现有引擎规则约束。没有新增任意状态编辑或自定义标签。

点击任务行「追踪」，在当前页面弹出该任务的执行记录，无需跳转到另一张表或手填 task_id。复用 GET /api/task/trace?id=<任务ID> 及后台鉴权；快速切换任务或更换登录身份时，旧响应不会覆盖新弹窗。未记录步骤时说明追踪未开启、任务未运行或记录已过保留期。独立 Trace 表格与通用状态探测接口不再在宿主挂载。

规则、样本、Agent、质量、配置及令牌继续通过各自的专用页面管理，不在此处挂原始数据表。业务表格 key 不得与 `task`、`operation_log` 冲突。

### 注册业务表格

```go
app, err := papa.New(papa.WithModels(&models.Episode{}))

// 在 New 之后、Run 之前注册（这样能用 app.DB 构造 Source）
app.UseTables(oao.Table{
    Key: "episode", Label: "剧集", Group: "业务",
    Source:  myEpisodeSource,          // 业务实现，负责查库/调接口
    Columns: []oao.Column{
        {Field: "id", Kind: oao.KindNumber, Width: "70px"},
        {Field: "title", Label: "标题"},
        {Field: "downloaded", Label: "已下载", Kind: oao.KindBool},
        {Field: "cover", Label: "封面", Render: oao.RenderImage, Size: 56},
        {Field: "remark", Label: "备注", Render: oao.RenderInput, MaxLen: 30},
    },
    Filters: []oao.Filter{
        {Field: "title", Label: "标题", Op: oao.OpLike},
        {Field: "downloaded", Label: "已下载", Kind: oao.KindBool, Op: oao.OpIn},
        {Field: "created_at", Label: "创建时间", Kind: oao.KindTime, Op: oao.OpBetween},
    },
    DefaultSort: "-id",
})
```

**操作列**（可选）：声明 `Actions` 才有，不声明就是只读表、不注册任何写路由。动作请求转发给业务的 `Handler`，
业务用 `oao.Fail` 返回带状态码的提示语（其他错误统一 500，细节不回前端）：

```go
Actions: []oao.Action{
    {Key: "retry", Label: "重投", Tone: oao.ToneInfo,
     Confirm: "重置该任务并重新投递？",          // 非空 → 先弹确认框
     Handler: func(ctx context.Context, req oao.ActionRequest) error {
         id, err := strconv.ParseUint(req.ID, 10, 64)   // 主键是字符串，取 Table.IDField 指定的字段
         if err != nil {
             return oao.Fail(http.StatusBadRequest, "无效的 ID")
         }
         // 防重复提交：把行快照里的版本值写进 UPDATE 的条件，并检查影响行数。
         // req.Row 是客户端回传的、不可信的展示快照，只适合当"版本号"用。
         if err := engine.RetryTask(uint(id), wasReprocess(req)); err != nil {
             return oao.Fail(http.StatusConflict, "%v", err)
         }
         return nil
     }},
    {Key: "fail", Label: "标失败", Tone: oao.ToneWarn, Confirm: "确认？",
     Form: []oao.Field{{Name: "reason", Label: "失败原因", Widget: oao.WidgetTextarea, Required: true}}},
    oao.EditAction(...),    // 表单字段由列声明推导（跳过图片/JSON/链接与 NoEdit 列）
    oao.RemoveAction(...),  // 自带二次确认
}
```

两条容易踩的约定：

- **主键列必须声明**：前端靠 `Table.IDField`（默认 `id`）指定的字段定位目标行，而列表下发时
  只保留**声明过的列**——没声明这一列，点按钮只会弹「这一行没有 id 字段」。不想显示就用
  `Hidden: true`（仍会下发）。`oao.New` 在注册时就会校验，声明不一致直接报错。
- **防并发/重复提交是业务的事**：组件只透传，不做去重（见 oao README 的「组件的职责边界」）。
  正确做法是把前置条件写进**自己的写语句**并检查影响行数，别用"先查再写"（TOCTOU 等于没锁）。

动作声明得多了也不会撑行：**超过 3 个时前两个平铺、其余自动收进「更多 ▾」**（面板支持键盘与点外部关闭）。

内置「任务」表（`admin/tasksource`）是动作如何接线的参考实现，它带了八个动作（见下表）——
写操作都走 `engine.Engine` 的条件更新，
`url` 列用 `NewTab: true` 在新标签页打开。成功与失败都会调 `Config.OnAction`，papa 用它写操作日志
（见 [CORE_CONFIG.md](./CORE_CONFIG.md) 的 `server.operation_log`，不开就不记）。

数据源只需实现一个方法：

```go
type Source interface {
    List(ctx context.Context, q oao.Query) (rows []map[string]any, total int64, err error)
}
```

`Query` 是组件把 HTTP 参数规范化后的结果（`Page/Size/Search/Sort/Filter`），
筛选算子（`In` 用 `"a,b,c"`、`Between` 用 `"a..b"`）由业务自己解释 —— 组件只透传。
papa 的 `admin/gormsource` 把算子落成 SQL：`OpLike` → `LIKE '%值%'`（前后通配，用不上索引），
`OpPrefix` → `LIKE '值%'`（只有后通配，能走索引），`OpEq`/`OpIn`/`OpBetween`/`OpGt`/`OpLt` 各对应同名条件。
参考实现看 `admin/tasksource`（内置「任务」表）或 hg2 的 `tablesource`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `{prefix}/tables` | 列出已注册的表格及列/筛选/操作元数据（二级导航用） |
| GET | `{prefix}/{table}` | 分页数据；query：`page`、`size`（默认取表声明，上限 200）、`search`、`sort`（`col`/`-col`）、`filter[col]=val` |
| POST | `{prefix}/{table}/action/{key}` | 转发操作给业务 Handler（表未声明该动作一律 404） |

`prefix` 默认 `/api/oao`；静态资源挂在 `/static/oao/`。**这几条 API** 走监控后台的白名单 + 密钥校验（组件复用宿主注入的中间件）；`/static/oao/` 与 `/static/mo.js` 一样**免鉴权**（浏览器 `<script src>` 带不了自定义请求头），所以别往组件自带的静态资源里放机密。

- **列怎么显示**：`Render` 可选 `text`（省略号 + 悬停看全文）/ `input`（只读输入框，
  长度可控、横向滚动看全，**不是编辑**）/ `link` / `image` / `enum`（彩色标签）/ `time` / `json` / `custom`。
  留空按 `Kind` 推断。
- **哪些能筛**：只声明需要的字段，未声明的字段不可筛；列名与排序同样走白名单，杜绝注入。
- **菜单自动出现**：归入对应类别，再按 `Group` 分组渲染二级导航，注册即出现，前端无需改代码。
- **刷新策略**：表格页只在用户操作（筛选/排序/翻页）时刷新，不参与 Dashboard 的 3 秒轮询。

可选的站点表组件（`admin/sitesource`，宿主需自行注册）展示**站点快照** —— 数据来自内存（引擎按声明重建、
暂停/恢复时整块回写；落点是 `crawler_config` 的 `sites` 键），**不走 SQL、也不单独一张表**。
它**只读**（原来的「轮询任务 / 暂停·恢复自动轮询」随按站点队列一起移除了），筛选/搜索/排序/分页
在内存里做（站点只有几行）。列里的 `base_url` / `stage_count` 是按声明抄的：**改声明要重启**。

内置的「任务」表（`admin/tasksource`）展示的就是 `crawler_tasks` 表，可作为完整示例。
它带七个写操作加一个只读入口（组件超过 3 个动作时只平铺前两个，其余收进「更多 ▾」）：

| 动作 | 位置 | 说明 |
| --- | --- | --- |
| **重投** | 平铺 | 重置为待处理并重新投递（队列满时与正常投递一致溢出到 DB 回灌），带 `reprocess` 版本条件防重复点击 |
| **追踪** | 平铺 | 打开该任务的**步骤时间线**：按「第 N 次尝试」分段，每段列出步骤名、耗时、失败步（红）与非致命步（橙，`task.Trace.Warn`）的错误分类与信息、以及该步采集到的数据（可折叠）。引擎自己也会补两条：「任务失败」（失败尝试的原因）与「归档页面」（失败那一刻的页面，带「下载这一页」按钮）。浏览器捕获/等待失败时还有「捕获网络请求」（候选请求列表，见下）与「等待渲染」（超时/实等，见下） |
| **加急** | 更多 ▾ | 把该任务投一份到所属阶段的**快车道**，插到排队任务前面执行。见下方说明 |
| **开轮询** | 更多 ▾ | 让该任务参与周期轮询：只改 `repeatable` 标记并把「下次轮询」置为现在，下一轮扫描才生效；已经开着再点 → 409 |
| **停轮询** | 更多 ▾ | 停掉该任务的周期轮询，已经跑起来的这一轮不受影响；已经停着再点 → 409 |
| **设轮询周期** | 更多 ▾ | 弹表单填周期（秒，0 = 用全局 `repeat_queue.interval`）；只改周期，不立刻重跑一次；带行快照版本守卫 |
| **标失败** | 更多 ▾ | 只对**待处理**的行生效（外加**上一轮崩溃留下的孤儿行**：`processing` 且 `updated_at` 早于本次启动 —— 那种行没有 worker 在跑，而它是 `recover_queue` 关着时唯一的人工出口）（排队中才拦得住：worker 认领以 `status=待处理` 为条件，标了就取不走），必填原因写进任务的错误信息；「处理中」的行拒绝 → 409（它已被 worker 认领，标失败会被 worker 完成时无条件写回，不是终态） |
| **删除** | 更多 ▾ | 二次确认；「处理中」的行拒绝删除 → 409（worker 稍后会对已删行写状态）。想让正在跑的任务停下用整站暂停，想重跑等它结束再用「重投」 |

写操作都是条件更新，业务错误经 `oao.Fail` 带状态码返回，成败都记入操作日志。

> **防重复提交有三层**：① 前端 —— oao 组件自己拦：同一「表 + 动作 + 行主键」在上一次请求
> 结束前再次触发会被 `runAction` 直接忽略，请求根本不发出去（oao v1.2.4 起；见其 README
> 「防重复提交」）；② 服务端 —— 每个动作的 `WHERE` 里都有版本守卫，重复请求影响 0 行、
> 返回 409，**这一层才是最终防线**（防的不只是手抖，还有两个人同时点和重放）；
> ③ 数据 —— 动作要改的状态本身写在小表里（如 `urgent`），看得见也查得到。
>
> 注意「加急」收在「更多 ▾」里，而那个面板是 `closeOnPick`（点完就收），所以它其实很难被双击命中；
> 防连点主要护的是平铺的「重投」。

**关于「加急」**：它只省**排队**时间 —— 该阶段 worker 全在忙的时候插队也快不了，
所以别指望它能把一条任务从 30 秒的浏览器抓取里"抢"出来。
实现上是给该阶段的池子加了一条快车道队列，worker 取任务时优先看它（`internal/workerpool`）。
几个边界：任务已在执行中 → 409「已经加急过了，或已被取走」；任务已成功/失败 → 409「已结束，
要重跑请用重投」；重复点两次 → 第二次拿到 409（`urgent` 列本身就是版本守卫）。
worker 认领时 `urgent` 自动归零，是**一次性**的，不会让失败重投的加急任务越积越多。
归零之后表上就看不出它加急过 —— 所以引擎同时在**步骤追踪的第一步**记一条「加急执行」
（只记第一次尝试），点「追踪」就能看出这条曾经加急跑过。这条依赖 `crawler.trace.enabled` 打开，
没开追踪时就只剩认领前后的 `urgent` 列可看。
任务表的「加急」列（是/否）显示当前状态。业务侧想在提交时就加急，用 `papa.Task{..., Urgent: true}`
（见 [FETCHER_WRITING_GUIDE.md](./FETCHER_WRITING_GUIDE.md) 1.2）。

**关于「开 / 停轮询 / 设轮询周期」**：某条任务**要不要周期性重跑**由任务行上的 `repeatable` 列决定、
**多久一次**由 `repeat_interval`（秒，0 = 用全局 `repeat_queue.interval`）决定 —— 粒度都是任务，不是阶段。
阶段声明的 `RepeatLimit` 也约束后台总按钮“轮询任务”：强制执行只忽略周期，不忽略次数上限。达上限不会关闭 `repeatable`，再次“开轮询”不会重置计数。需要继续周期轮询时调整阶段上限；单条“重投”、恢复队列和错误队列不受该上限限制。详见 [REPEAT_QUEUE.md](./REPEAT_QUEUE.md)。

首次提交时由 `papa.Task{Repeatable: true, RepeatInterval: 10*time.Minute}` 播种，之后就用这三个动作改
（业务里等价的入口是 `engine.SetTaskRepeatable(id, on)` / `engine.SetTaskRepeatInterval(id, was, seconds)`，
见 [REPEAT_QUEUE.md](./REPEAT_QUEUE.md) 第 3 节。任务表上有对应的三列：**轮询周期(秒) / 上次轮询 / 下次轮询** ——
队列只按「下次轮询」到点投，改周期会连带重算它。
三个动作都**只改标记**：下一轮扫描时才生效（开轮询会把"下次轮询"置为现在，所以它就是下一轮），
**不会**顺手立刻重跑一次（想立刻跑请用「重投」）；已经开着再开、已经停着再停都返回 409
（`repeatable` 这一列本身就是版本守卫，「设轮询周期」用的是行快照里的旧周期值，与 `urgent`/`重投` 同一思路）。
「停轮询」也不打断已经跑起来的那一轮 —— 它跑完这次就没有下一次。
注意**停轮询 ≠ 放开去重**：行还在（`success`/`failed`），同 `site:stage:url` 再提交仍会被静默吞掉，
要立刻重跑只能用「重投」。

**关于「追踪」**：这个动作在服务端**不做事**，只回一句成功 —— 因为表格组件的动作成功时只能回
`{"status":"ok"}`、带不回数据，而组件也没有对外的事件钩子。真正的展示由
`/static/trace.js` 接管：它包了一层 `window.fetch` 嗅探这次动作请求，从请求体里取出任务 id，
再自己拉 `GET /api/task/trace?id=<id>`。所以点「追踪」时那句「追踪成功」的 Toast 是组件的
固有行为，不是多余提示。

抽屉里失败尝试的最后一条是**引擎补的**「任务失败」（错误分类 + 消息）—— handler 不必自己再上报一次；
若这一次抓到过页面，前面还有一条「归档页面」，那一步带「下载这一页」按钮（`GET /api/task/page?file=`，
回的是文件本身），拿下去对着真实页面改选择器最省事（配置见 [CORE_CONFIG.md](./CORE_CONFIG.md) 的 `archive` 一节）。

浏览器抓取的失败现场会多两步（`engine.CaptureRequest` / `FetchRenderedPageWith`，见
[FETCHER_WRITING_GUIDE.md](./FETCHER_WRITING_GUIDE.md) §5）：

- **`捕获网络请求`**（失败）：步骤头显示「超时 30s · 实等 30.2s」，展开后是**期间发出的请求样本**
  （`METHOD URL`，最多 20 条，总数在标题上）。用来区分「一个请求都没发」「发了但域名换了」
  「路径改版」三种死法 —— 这三种的修法完全不同。
- **`等待渲染`**（失败）：步骤头同样带超时/实等，data 里有卡住的步骤（selector / js /
  request-idle）与对应的选择器或表达式。

两步的现场 HTML 都会登记进归档（与「归档页面」同一条链路），所以抽屉里的顺序是
「捕获/等待失败 → 归档页面（下载）→ 任务失败」。渲染判据是 data 里的键（`candidates` /
`timeout_ms`），不是步骤名 —— 步骤名微调不会让展示静默失效。

步骤追踪需要在配置里显式开启（`crawler.trace.enabled`，见 [CORE_CONFIG.md](./CORE_CONFIG.md)），
handler 侧的用法见 [FETCHER_WRITING_GUIDE.md](./FETCHER_WRITING_GUIDE.md) 1.3。
**未开启时点「追踪」不会白屏**，抽屉里会直接显示「步骤追踪未开启」。
要先跑一次迁移把 `crawler_task_trace` 建出来（脚手架项目里 `make migrate` 与 `papa migrate` 等价）；开关开着但表不存在时，
启动会打一条醒目的错误日志，不会静默丢数据。

## 4. 自定义页与注入（逃生舱）

声明式的表格页覆盖不到的场景（自定义看板、审核页、特殊展示），可以往后台加**自定义页**，
或直接注入受信任的 JS/CSS。四个 API 都在 `Run` 之前调用：

```go
// 一页 = 类内一个入口 + 一段渲染脚本
app.UsePage(papa.Page{
    Key: "review", Label: "审核", Group: "业务",   // Key 只允许字母数字下划线连字符
    Section: "flow", // 可选：flow / monitor / data / system
    Script: `
        Papa.page("review", function (el, meta) {
            // el 是页面容器；meta 提供 {key,label}
            el.innerHTML = '<h2>' + esc(meta.label) + '</h2>';
            apiFetch('/api/my/review-list').then(r => r.json()).then(function (d) {
                el.innerHTML += '<p>共 ' + d.total + ' 条待审</p>';
            });
        });`,
})

app.UseScript(`window.__myFlag = true;`)      // 全局注入一段 JS
app.UseScriptFile("assets/admin.js")          // 读文件注入（读不到直接 panic）
app.UseCSS(`.my-badge { border-color: var(--primary); }`)
app.UseCSSFile("assets/admin.css")
```

`Page.Section` 可取 `flow`、`monitor`、`data`、`system`。省略或未知值统一回退 `data`；原 `Group` 保留为类内标签，旧业务无需改代码就可访问。该分类只控制入口位置，不授予权限。

前端契约：页脚本在加载后调 `Papa.page(key, fn)` 注册渲染函数，点菜单时框架调用 `fn(el, meta)`。
页面脚本里可以直接用后台的全局件：`Toast` / `Dialog` / `skeletonRows` / `esc` / `tipAttr` /
`apiFetch` / `apiPost`（都带密钥）。没注册渲染函数的页会显示一句明确提示，不会白屏。

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/pages` | 白名单 + 密钥 | 自定义页清单（二级导航用），`{"pages":[{key,label,group,section}]}` |
| GET | `/static/custom.js` | **免鉴权** | `UseScript` / `UsePage` 的脚本拼在一起 |
| GET | `/static/custom.css` | **免鉴权** | `UseCSS` 的样式（在 mo.css / oao.css 之后加载，可覆盖） |

> **注入内容按"非机密"对待**：浏览器加载 `<script src>` / `<link>` 时带不了自定义请求头，
> 所以这两个端点走的是和 `oao.js` / `mo.js` 一样的免鉴权静态路由 —— **别把密钥、令牌之类的敏感值写进注入的 JS/CSS**。
> 数据接口仍然全部在白名单 + 密钥后面（清单 `/api/pages` 就是要密钥的）。
>
> 声明有问题（Key 非法 / 重复 / Script 为空 / 注入文件读不到）会在启动时 **panic**，不会等到点了菜单才发现。

## 5. 自定义路由与中间件（Go handler）

表格页与自定义页覆盖不到的场景（自定义看板的后端接口、审核动作、对接外部系统的回调），
可以直接往后台挂自己的 **Go HTTP handler**，并串上自己的中间件：

```go
app.UseRouter(func(r *papa.Router) {
    r.Use(accessLog)                       // 中间件：注册顺序正序执行，只对之后注册的路由生效
    r.Group("/api/review", func(g *papa.Router) {
        g.Get("/list", listHandler)        // GET  /api/review/list
        g.Post("/approve", approveHandler) // POST /api/review/approve
    })
    r.Handle("PATCH /api/review/note", noteHandler) // 其余方法用 Handle；pattern 是 Go 1.22 的 ServeMux 语法
})
```

| 方法 | 说明 |
| --- | --- |
| `Use(mw ...Middleware)` | 追加中间件（`func(http.Handler) http.Handler`），正序执行，只影响之后注册的路由 |
| `Group(prefix, fn)` | 子路由组：前缀相加、继承父组中间件 |
| `Get/Post/Put/Delete(pattern, h)` | 常用方法的快捷方式 |
| `Handle(pattern, h)` | 任意方法；pattern 可带方法前缀（`"PATCH /api/x"`） |
| `NoAuth()` | 返回一个**不带后台鉴权**的组视图（见下） |

**鉴权默认开着**：业务路由和后台内置接口一样过「IP 白名单 + 访问令牌」（**不看路径前缀** ——
注册在 `/internal/x` 这种路径上照样要令牌），自定义页里用
`apiFetch` / `apiPost` 调它会自动带上凭据。后台鉴权套在**最外层** —— 白名单/令牌没过的请求
根本不会进你的中间件，所以日志、计数这类带副作用的中间件不会被未鉴权流量污染。

**要对外公开的接口**（webhook、OAuth 回调、健康检查）用 `r.NoAuth()` 显式声明：

```go
r.NoAuth().Post("/webhook/github", webhookHandler) // 对白名单外、没带令牌的来源也开放
```

它是有意为之的逃生舱 —— 默认松掉鉴权才是危险的，所以要求明确写出来。`NoAuth()` 返回的是副本，
不影响原组；在子组上调用时前缀照旧生效。

几条约定：

- **必须在 `Run` 之前注册**（路由在 `Run` 时挂载），且要求 `server.enabled: true`。
  注册了却没挂上**不会静默**：启动会打一条醒目错误日志说明有 N 组路由没生效。
- 回调传 `nil` 直接 panic（与 `UsePage` / `RegisterSites` 同风格：声明有问题启动即失败）。
- pattern 与现有路由冲突时是 `http.ServeMux` 的 panic（挂在同一个 mux 上），不会悄悄覆盖。
- 业务路由走的是同一道 `Monitor.Auth`：**不管路径是否以 `/api/` 开头**，白名单与令牌都要过
  （`NoAuth()` 的组除外），`Cache-Control: no-store` 也由它统一加上 —— 需要的话自己在 handler 里覆盖。

`papa new` 生成的工程把这套东西放在 `internal/monitor/` 包里分层：`router.go` 声明路由与中间件、
`controller/` 放 handler、`middleware.go` 放中间件、`tables.go` 放表格页、`view/` 放自定义页。
表模型不在这层 —— 和 `fetcher/` 同级放在项目根的 `models` 包（建表清单 `models.Models()`），
爬虫业务与后台服务共用。`main.go` 只需要 `monitor.Register(app)` 一行，各层分工见每个文件顶部的包注释。

## 6. 队列治理

「采集任务流 → 异常处理」展示**两个全局治理队列**：错误队列（`error_queue`）与轮询队列（`repeat_queue`），
**各占一行**，都能单独手动触发 —— 不再按站点拆（错误队列重投所有站点符合条件的失败任务，轮询队列投所有已到点的 repeatable 任务）：

> `recover_queue` **不在这个面板上**：它只在进程启动那一刻跑一次，没有周期、没有积压可看，
> 也就没有「立即执行一次」的意义。其公开方法仅供引擎启动恢复流程使用；不要把它接成运行期按钮或定时任务，以免恢复语义与正在执行的任务生命周期交叉。
> 见 [RECOVER_QUEUE.md](./RECOVER_QUEUE.md)。

| 列 | 含义 |
| --- | --- |
| 状态 | `运行中`（附带本轮已执行时长）/ `空闲` / `已停用`（配置里没写这段，或 `enabled: false`）；有上次执行错误时鼠标悬停可见 |
| 上次执行 | 上次执行完成距今多久（悬停看绝对时间）· 上次执行耗时 |
| 处理量 | 空闲时=上次处理数，运行中=本轮已处理数；副行显示累计处理数 |
| 待处理 | 当前排队待处理的任务数（低频采样，副行显示采样时间） |
| 操作 | 立即执行一次该队列（**写一条操作日志**） |

手动触发的 HTTP 接口（等价于页面上的「立即执行」，同样写操作日志）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/errorqueue/process` | 手动触发失败任务重投；返回 `{"status":"ok","processed":N}` |
| POST | `/api/repeatqueue/process` | 手动触发周期轮询（重投**到点的** repeatable 任务；想强制某一条立刻重跑用任务表的「重投」）；返回 `{"status":"ok","repolled":N}` |

数据来源分两类，均**不实时**，且不占用监控页刷新路径：

- 运行状态/耗时/处理量：引擎内存计数，随队列执行即时更新。
- 待处理积压：`COUNT` 查询，由后台按 `server.queue_sample_interval`（默认 `1m`）低频采样；每轮队列执行结束也会立即补采一次。采样频率越低，DB 压力越小。
- 采样仅在 `server.enabled: true` 时启动。

对应的 `/api/monitor` 响应字段：

```jsonc
"queues": {
  "error_queue":  { "name": "error_queue",  "enabled": true, "running": false, "runs": 12, /* … */ },
  "repeat_queue": { "name": "repeat_queue", "enabled": true, "running": false, "runs": 0,  /* … */ }
}
```

队列的参数（`enabled` / `worker_count` / `interval` / …）取自 `config.yaml` 的全局段
（见 [CORE_CONFIG.md](./CORE_CONFIG.md)）。

`last_duration` / `started_at` 等时间字段：`duration` 为纳秒，时间为 RFC3339。

### 站点 Tab：多站时按站点把面板分开

多站点时，内容区顶部会多一排**站点 Tab**（「概览（全部）」+ 每个站点一个；数据来自 `/api/monitor` 的 `sites`，
由声明在启动时构建、存在 `crawler_config` 的 `sites` 键里）：

| 面板 | 切到某个站点 tab 时 |
| --- | --- |
| 阶段/池子（仪表盘） | 只显示**该站**的阶段（阶段快照里现在带 `site`） |
| 任务队列概览（仪表盘） | 概览=**按站点分卡片**（每站一张，卡内每阶段一行：排队 / 未完成（含排队） / 错误 + 完成小字）；切到某站后显示该站的多阶段完整详情（五格 tiles + 累计耗时 + Worker 明细表） |
| 异常处理 | **全局范围** —— 两条队列全站各一条，页面隐藏站点筛选 |
| 站点概要（tab 下面那行） | BaseURL / 阶段数 / 是否被手动暂停 |
| **暂停铃铛**（右上角） | **不过滤** —— 它是告警，切到哪个 tab 都看得到、面板里也列全部被闸住的站 |
| **站点控制**（卡片） | **跟着 tab 走**：切到某站只留那一行；概览显示全部站点（当总控台用） |
| 任务表（表格页） | **跟着 tab 走**：切到某站再打开任务表，会带着 `site=<该站>` 的**预置筛选**打开（oao 的 `opts.filter`，筛选栏里填好、可改可清）；已开着表时切 tab 会按新站点重画。概览 → 不带筛选。**需要 oao ≥ v1.3.0**（带 `opts.filter` 的那版），老版本会静默忽略第三个参数 |

运行概览展开「阶段与 Worker 明细」后，「任务队列概览」在**概览（全部）**下按站点分卡片：每站一张卡，卡内每个阶段压成一行（阶段名 + 排队/未完成（含排队）/错误三个数字 + 完成小字），多站都叫 catalog/detail 时也能一眼分清是哪站在排队/出错；站点没有活跃阶段时卡里显示「暂无活跃阶段」。**切到具体站点 tab** 后显示该站的完整阶段详情：每阶段五格大数字（排队/未完成（含排队）/完成/错误/已提交）+ 累计耗时行 + **Worker 明细表**（每个 worker 的任务数/失败数/耗时），不压缩 —— 原独立「任务队列」模块已并入这里，侧边栏不再单列。

> 站点概要与 `sites` 里的字段：`key / base_url / stage_count / breaker_paused / breaker_paused_at`。
> `base_url` 与 `stage_count` 是**启动时按声明抄的**（改声明要重启；直接改库不生效）。
> `breaker_paused*` 这一对由**后台手动暂停/恢复**与**启动期 `StartPaused` 播种**写（熔断触发不写它 ——
> 它只往引擎的暂停信号里写）：手动暂停时含义是"被手动停着"，要看熔断触发请点右上角铃铛
> （`breakers[]` 的 `source`）。声明了 `StartPaused` 的站每次启动都按**本次启动时刻**重新写成暂停态
> （随启动快照一次写回，不再逐站补写）。
> 「每站每阶段的池子统计」是**实时**数字，不落库 —— 它就在 `stages` 快照里：**键是 `site:stage`**
> （阶段名只在本站内唯一，两个站的 `catalog` 是两条），条目里另带裸阶段名 `stage` 与 `site` ——
> 站点 Tab 按 `site` 分组，面板标题用 `stage`。

```jsonc
"sites": {
  "example": {
    "key": "example", "base_url": "https://example.com/", "stage_count": 3,
    "breaker_paused": false, "breaker_paused_at": "0001-01-01T00:00:00Z"
  }
}
```

## 8. obs 报告

「运行监控与报告 → 运行报告」把
`obs.report.dir`（默认 `./reports`）下的**历史运行报告**列出来，不用登服务器就能看产物原文、下载。
报告由**定时任务**（`obs.report.interval`）、**进程退出**（`obs.report.on_exit`）或命令 `papa report` 写入，
**一份报告 = 一个目录**
（默认按本地日历日拆分：`<obs.report.dir>/<2006-01-02>/`，一份 = 一天；`--run` 例外，单份 `<obs.report.dir>/<run_id>/`），
目录里固定四份产物（产物口径见 [OBSERVABILITY.md](./OBSERVABILITY.md)），头部与 JSON 里都带**生成时间（最近一次更新）**：

| 文件 | 内容 |
| --- | --- |
| `report.md` | 人读：生成时间、判定、问题清单（含证据）、运行概览、队列/耗时、失败分组、检查段 |
| `report.json` | 机读：同源结构化数据（`generated_at` / `mode` / `verdict` / `verdict_reason` / `run` / `events` / `logs` / `degraded` / `engine` / `inputs` / `sections` / `checks` / `problems`） |
| `ai-brief.md` | 给 AI / 接手排查的人：生成时间、环境事实、问题证据 + 假设 + 验证命令 + 修复方向、下一步 |
| `ai-brief.json` | 同构机读版本（含 `generated_at`） |

**报告列表**（每行一份报告，按生成时间倒序）：目录名、判定、生成时间、文件数、「查看」。
判定单元格除了判定徽标，还会带：`mode=snapshot` 的「快照」徽标、`engine_paused=true`（报告里任一站点暂停）的
「引擎暂停」徽标、以及 `fail_reason_top`（最多 3 条未通过检查的 ID，给判定补一句「为什么红」）。
生成时间优先用 `report.json` 的 `generated_at`，没有这个字段的旧报告退回目录修改时间。
目录名通常是**日报日期** `YYYY-MM-DD`（一份 = 一天），升级前留下的 `run_id` / `window-*` 目录也照常列出。
判定读的是 `report.json` 的 `verdict`，翻成「通过」/「带风险通过」/「不通过」/「未判定」，读不到（缺 `report.json`、
文件坏了）也显示「未判定」。文件数显示 `已有份数 / 4` —— 缺文件的半份报告照列；只要目录里
至少有一份已知产物就会被列出，报告目录里手工放的无关目录/文件不会出现在列表里。

**报告内容**：选中一份后，页内出现四个产物对应的文件 Tab（只列实际存在的），
**按纯文本展示原文**（前端放进 `<pre>`，不渲染 markdown）；「下载当前文件」把当前 Tab 那份按附件下载。

切换报告或文件 Tab 后显示加载状态，正文和读取失败提示只对应最后一次选择；旧请求晚到不会覆盖当前报告。选中没有产物的报告时，旧内容也不会重新出现。

空态两种：`obs.report.dir` 没配 → 页面提示「报告目录未配置」；配了但目录里还没有报告 →
提示先跑一次 `papa report`（或开 `obs.report.on_exit` 让进程退出时自动生成）。

报告目录的保留期由 `obs.report.retention` 控制（默认 7 天，负数 = 永久保留）；过期目录是**生成报告时**
清掉的（见 [OBSERVABILITY.md](./OBSERVABILITY.md)），后台这个页面只展示、不删除。

接口（和其它后台接口一样过 IP 白名单 + 访问令牌，见 §1）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/obs/reports` | 报告列表：`{"report_dir":"…","runs":[{"name":"…","verdict":"pass","mode":"acceptance","engine_paused":false,"generated_at":"…","fail_reason_top":["event_coverage"],"mod_time":"…","files":[{"name":"report.md","size":1234,"mod_time":"…"}]}]}`。`verdict` / `mode` / `engine_paused` / `generated_at` / `fail_reason_top` 从 `report.json` 读出，旧报告缺字段就省略（`engine_paused=false` 也省略）；`fail_reason_top` 最多 3 条、只列未通过的 fail/warn 检查 ID；最多回 100 份（按生成时间倒序，无 `generated_at` 的退回目录 mtime）；`report_dir` 没配 / 目录不存在都回空列表（不是错误） |
| GET | `/api/obs/report?run=<目录名>&file=<四份产物之一>` | 单份产物原文（`text/plain; charset=utf-8`）；`download=1` 时带 `Content-Disposition: attachment; filename="<run>-<file>"` |

**报告里是日志、URL 等不可信文本**，所以这几条边界是硬的：

- **纯文本到底**：接口固定 `text/plain` + `X-Content-Type-Options: nosniff`，前端只往 `<pre>` 里塞文本，
  不渲染 markdown —— 报告内容是外部输入，渲染面就是注入面。
- **只认四份固定产物**，`run` / `file` 都必须是**单段名字**：空、`.`、`..`、含 `/` 或 `\`、
  含 `:`（Windows 盘符 / 备用数据流）一律 **400**；`file` 不在四份产物里同样 400，
  解析后越出报告根目录也 400。
- 单份产物超过 **16MB** 回 **413**（报告是给人看的文本，正常几百 KB，过大多半是目录被换成了别的东西）；
  目录没配置时读接口回 **404**，文件/运行目录已被清理回 **404**（列表接口仍回空列表）。

## 9. 暂停与熔断

**暂停只有一处状态**：引擎的暂停信号（`engine/pause.go`），按 scope 记（整站或某站的某阶段）、
带原因与来源。两个地方读它、两层一起生效：

| 层 | 位置 | 语义 |
| --- | --- | --- |
| **取任务点** | 每个工作池绑的闸门 | **冻住**：worker 停在取任务之前，队列里已经躺着的那批也不动，在途任务跑完为止 |
| **入队点** | `submitToStage` | **收口**：不再接新活，任务寄放到溢出表（溢出积压会涨），「恢复」时立刻灌回 |

**两层各有一个粒度**（同一张信号表，只是 scope 不同）：

- **站点那一层**（`scope`）= **管这一站的全部阶段** —— 包括后台列表里根本看不到的那些
  （`detail` / `episode` 这种由上一级投出来的）。**框架自带的界面只做到这一层**（「站点控制」卡上那个
  「暂停整站」）：它是唯一不需要站点知识的粒度（"这一站先别抓"）。
- **阶段那一层**（`scope` + `stage`）= 只掐那一个阶段，别的照跑（"catalog 先别抓、让 detail 跑完"）。
  这是**接口**，框架不替业务决定界面长什么样 —— 见 §10 的"阶段级控制是接口，不是框架的界面"。

**暂停不跨重启**：进程重启即恢复运行（起进程本身就是一次人工介入）。要长期停就**改声明** ——
`SiteSpec.StartPaused: true` 让这一站每次启动都先闸住（入口任务照投、任务寄放在溢出表里），
等你在后台「站点控制」卡上点「恢复整站」；声明期这一道是"每次启动重新闸上"，
运行期在后台点的暂停/恢复不会被它改回去。也可以在部署层面停进程 ——
但别指望运行期点一下「暂停」能撑过一次重启。

**来源只有两种**（payload 里的 `source`）：`manual`（后台/业务手动）与 `breaker`（熔断自动触发，
见下）。**熔断只是"自动往这张表里写一条的人"** —— 它自己数窗口内的终态失败、比阈值、发
`AlertCritical`，停与不停、现场怎么写、铃铛怎么画都归暂停信号。

### 暂停与告警都在右上角那只铃铛上

**为什么不是横幅**：声明了 `SiteSpec.StartPaused` 的站一加载就停着，横幅就成了每次打开后台都压在
首屏的一大块（把正文挤下去），而它平时什么也不必说。于是压成一只铃铛：

| 元素 | 含义 |
| --- | --- |
| **徽标数字** | 被闸住的 scope 数（含声明期的 `StartPaused`），没有就整个隐藏 |
| **徽标颜色** | 有熔断触发（`source=breaker`）就是**红的**（出事了）；只有手动/声明期就用**琥珀**（是你自己让它停的） |
| **脉冲** | 页面开着时**新出现**熔断触发 → 铃铛抖两下。首帧不抖，`StartPaused` 这种"一加载就停着"也不算新告警 |
| **点开** | 在铃铛下方弹出面板，逐 scope 一块（见下）；再点一次、点面板外部、按 Esc 关闭 |

徽标与面板的内容跟着 `/api/monitor` 每轮刷新一起来（**不额外发请求**），所以别的标签页里触发的暂停，
这边几秒内也能看到。**它不跟站点 Tab 过滤** —— 告警不该被切走的 tab 藏起来（跟着 tab 走的是
仪表盘上那张「站点控制」卡：那张是控制视角，铃铛是告警视角）。

**每个站点一条独立的暂停**（阈值按站点配：`SiteSpec.Breaker`，见 FETCHER_WRITING_GUIDE.md 7.2），
面板里**逐 scope 一块**：第一行是站点 + 结论 + 「恢复」按钮，第二行用等宽小字写细节 —— 哪一站（站点是必填维度，没有空键那一档）、哪个阶段、窗口内多少次
终态失败、暂停于何时，并各带一个「恢复」按钮（只放行那一站）；两个以上被闸住时额外给一个「全部恢复」。

**手动暂停与熔断触发在面板上是两种说法**（看 `source`，不再靠猜）：熔断触发一定带着阶段与
"窗口内 N 次失败，阈值 M"；后台手动按的（「站点控制」卡上那个「暂停整站」）显示成
`抓取已暂停（后台手动暂停）`；声明 `StartPaused` 的站启动时就停着，显示
`抓取已暂停（站点声明 StartPaused）` ——
不然会读出"阈值 0 / 0 次失败"这种幻觉（熔断没启用时阈值本来就是 0）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/breaker` | 各站点的状态：`{"breakers":[...]}`（按站点名字典序） |
| POST | `/api/breaker/resume` | 放行。**不点名 = 全部站点**；点名：`?scope=siteb` 或请求体 `{"scope":"siteb"}`。未知 scope 回 **400**（不静默放行全部） |
| POST | `/api/breaker/pause` | 暂停。**必须点名**（`{"scope":"siteb"}`）；不点名回 **400** —— 放行是往安全方向走，暂停是往危险方向走，一个误点不该把全部站点停掉 |

两个端点都再认一个可选的 **`stage`**（同上：query 或请求体）：给了就只动那一站的**那一个阶段**
（`{"scope":"siteb","stage":"catalog"}`），不给就是整个站点那一层。**给了 `stage` 却没给 `scope` 回 400**
（阶段属于某个站，不能当成"整站"或"全部"）。

`resumed=false` 表示**当前本来就不在暂停态**（比如另一个人先点了），这不是错误 ——
重复点击恢复不该看起来像失败，但也不能回一个含糊的 ok 让调用方以为是自己放行的。
放行了哪些 scope 在 `resumed_scopes` 里。

暂停与放行都是**人在场的干预**（它们停 / 通的是整条抓取线），所以状态真的变了之后会写一条操作日志
（`Table: breaker` / `Action: pause` 或 `resume`，带操作人与 `scope`）—— 前提是开了 `server.operation_log`。
「本来就在暂停态」那种空点不记（没有状态变更），也不报错。

`/api/monitor` 里的 `breakers` 数组（每项就是下面这个对象；`site` 是这个 scope 的站点键）：

```jsonc
"breakers": [
  {
    "enabled": true,
    "site": "example",    // 哪个站（站点是必填维度，没有空键那一档）
    "window": 300000000000, // duration 是纳秒
    "threshold": 50,
    "in_window": 12,        // 实时值：当前窗口内的终态失败数
    "paused": true,
    "paused_at": "...",
    "resumed_at": "...",
    "reason": "窗口内终态失败数达到阈值",
    "source": "breaker",    // 这条暂停是谁下的：manual（后台手动）/ breaker（熔断自动触发）
    "stage": "catalog",   // 触发的阶段（裸名）；哪个站看上面的 "site"
    "failures": 50
  }
]
```

另一处能看出站点的是**告警**：任务终态失败与熔断触发都走同一套 `Notifier`，事件里带
`site`（`papa.TaskError.Site`）—— webhook 那头可以据此路由（@对应的负责人）。

## 10. 站点控制（整站暂停 / 恢复）

仪表盘上的**站点控制**面板：**一站一行**，写清这一站现在跑不跑（`运行中` / `已暂停`），
右侧是「暂停整站 / 恢复整站」—— 它就是 §9 那条暂停信号在**站点那一层**的开关。

为什么只有这一档：**站点是唯一不需要站点知识的粒度**（"这一站先别抓"谁都能判断），
也是后台**唯一**主动停下来的入口 —— 铃铛面板只在已经闸住时才列出东西、只有「恢复」。
阶段那一层（只掐某一个阶段）框架**给接口、不做界面**，见本节末尾。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/breaker/pause` | 暂停：`{"scope":"example","stage":"catalog"}`（`stage` 省略 = 整站那一层）。**scope 必填** —— 一个误点不该停掉所有站 |
| POST | `/api/breaker/resume` | 恢复：同上；省略 scope = 全部放行（铃铛面板里那个「全部恢复」） |
| GET | `/api/monitor` 的 `breakers` | 各站的暂停状态快照（前端就靠它画铃铛的徽标与面板，不额外发请求） |

### 声明期就停住：`SiteSpec.StartPaused`

想在**启动那一刻**就停着（"先把入口排好、再放开这一站"、"上线后先看一眼队列再放量"），
在站点声明里写一行：

```go
// sites/example.go
SiteSpec{ Key: "example",
          StartPaused: true, // 每次启动都先闸住整站
          Stages: []papa.StageSpec{ /* … */ } }
```

引擎在 `ApplyRegisterStage`（HTTP 服务起来之前、投入口任务**之前**）据此下一道**整站暂停**：

- 入口任务**照投**（阶段声明写了 `Entry: true` 的那些）—— 但它们、以及启动恢复与轮询队列捞回来的任务
  全都在入队点折回溢出表（溢出积压会涨），**池子一个都不建**、worker 一条都没跑；
- 后台点「恢复整站」（`ResumeSite`）才灌回，`wakeDrainNow` 立刻叫醒回灌循环，不等下一个 drain tick；
- **暂停不跨重启**：每次启动都按声明重新闸上；运行期在后台点的那次恢复，不会被声明改回去。

> **别用入口开关表达"先别跑"**：`StageSpec.Entry` 只回答"这个阶段有没有入口任务"，
> 它管不住这一站的其它阶段 —— 启动恢复（`recover_queue`）与周期轮询（`repeat_queue`）
> 照样会把已经入库的任务跑起来，看着像"声明没生效"。要"这一站现在别动"，用 `StartPaused`。

这张卡只**显示**状态、只做**整站**那一档：没有入口行的阶段（`detail` / `episode` 这种由上一级投出来的）
同样受它管 —— 「暂停整站」停的就是这一站的全部阶段。

### 阶段级控制是接口，不是框架的界面

"只掐某一个阶段"（比如 `catalog` 先别抓、`detail` 照跑）框架**给的是接口，不做界面** ——
要不要在后台开到这个粒度、按什么层级呈现，由业务自己接：

| 接口 | 形态 |
| --- | --- |
| HTTP | `/api/breaker/pause` 与 `/api/breaker/resume` 都认一个可选 `stage`：`{"scope":"example","stage":"catalog"}`（只动那一个阶段；**给了 `stage` 没给 `scope` 回 400**） |
| 引擎 | `Engine.PauseStage(site, stage, reason)` / `Engine.ResumeStage(site, stage)`；读状态用 `Engine.BreakerStatuses()[site]`（`paused` / `source` / `stage` / `reason` 都在里面） |
| 前端 | 静态文件里的 `pauseCrawling(site, stage)` / `resumeCrawling(site, stage)` 也是这个签名，注进来的页可以直接调 |

接法就是本仓现成那两条扩展点：`app.UsePage` 注入一个页 + `app.UseRouter` 加一条路由（见 §4/§5），
或者干脆只用 HTTP 接口写个脚本 —— 框架不替你选。

参数走**请求体**而不是 query string 是有意的：站点键与阶段名除了不能带 `:` 什么都允许
（空格、`&`、中文……），塞进 `?site=` 会被 URL 编码坑。

暂停与恢复都会写一条操作日志（`Table: breaker` / `Action: pause` 与 `resume`，带站点、阶段与操作人）——
前提是开了 `server.operation_log`。声明期那道 `StartPaused` 不算人工操作，不写审计。


### 运行日志查看

「运行监控与报告 → 运行日志」采用紧凑文件列表，显示文件名、大小和“查看”。点击查看打开纯文本弹窗，仅显示最后最多 200 行；可刷新，空文件显示“暂无日志”。单次最多读取 1 MiB，超长行触发上限时显示截断提示。文件轮转或消失时提示刷新重试。文件以单列呈现，列表最多占视口高度的 65%，更多文件在内部滚动。列表与打包仅包含 .log、.log.gz 及数字轮转日志，忽略 .gitkeep、crawler.pid 等非日志文件。

下载统一使用标题右侧“全部打包下载”。已有单文件下载接口保留兼容，但运行日志页不提供单文件下载入口。压缩轮转文件不能直接查看，需全部打包下载后解压。

兼容的单文件下载与尾部查看共用日志目录边界和文件检查：只允许日志命名规则内的普通文件，拒绝路径参数、符号链接和其它文件类型，并通过 `os.OpenRoot` 限定目录。单文件下载保留 `.log.gz`、数字轮转文件及 HTTP HEAD/Range 支持；未传文件名仍走打包下载，鉴权要求不变。

新增 `GET /api/logs/tail?file=文件名`，沿用后台令牌与 IP 白名单鉴权，禁止缓存；仅访问配置日志目录下的普通文件，拒绝路径穿越和符号链接。响应包含 `name`、`text`、`lines`、`truncated`。读取以打开文件的大小快照为准，追加内容在下次刷新展示。


## 11. 周期批次中心

「采集任务流 → 周期批次」按顶部站点范围展示持久控制任务。点击「查看批次」可查看当前 BatchID、序号、固定发布代次、各阶段规则版本、待处理/处理中/成功/失败计数以及成员。控制任务的「成功」只表示本次调度成功；是否整批完成以详情计数为准。

- 列表每页 20 条，成员每页 50 条，均按 ID 升序游标分页。详情支持「只看失败成员」。仅进入页面、翻页和显式刷新时查询，不随监控轮询反复扫描成员。
- 控制状态、批次状态、聚合和本页成员在 MySQL 的同一只读 Repeatable Read 事务中读取，单次限时 3 秒。跨页不是永久快照；批次已切换返回 409，请刷新当前批次。
- 可停止/恢复控制任务轮询、重试本次调度、原批重试失败成员，或者打开原有 Trace/证据入口。停止轮询不取消已提交成员；重试控制任务不会强制开始新批次。
- 写操作复用 `/api/oao/task/action/*`，没有另一套绕过条件检查的写接口。启用 `server.operation_log` 后沿用任务动作审计，成功/失败均记录。仍沿用现有访问令牌权限，不新增角色模型。
- 任务表增加「任务类型」和任务 ID 筛选；仅下发派生角色，不下发原始 Meta。批次成员不提供开独立轮询、设周期和删除，成功成员不提供重投；控制任务也不提供删除。服务端从数据库识别角色，客户端伪造角色不能绕过。
- Engine 拒绝上述破坏批次的动作，返回 `ErrTaskBatchProtected`（HTTP 409）；成员重投的失败状态、不可轮询状态与 reprocess 一起进入 UPDATE。旧版本误开成员轮询时仍可「停轮询」。普通任务的原有动作保留。
- Meta 同时声明控制任务和批次成员时视为异常，禁止删除、重投、开轮询和改周期，仍允许关闭误开的轮询。误开轮询的失败成员不显示重试按钮，详情提示先到任务表关闭轮询。周期为 0 显示「使用站点默认周期」，不表示零间隔调度。

| 只读 API | 参数与结果 |
| --- | --- |
| `GET /api/rule-schedules` | 可选 `site`、`after`（最后一个 ID，初始 0）；返回 `items`、`next`，next 为字符串 `"0"` 表示末页 |
| `GET /api/rule-schedules/detail` | 必填 `id`（控制任务 ID）；可选 `after`、`batch`、`failed=1`；非零 after 必须带当前 BatchID；返回 `control`、`batch`、`rules`、`members`、`next` |

新端点沿用 IP 白名单和 Bearer 鉴权，禁止缓存；只允许 GET。ID/next 在新投影中为十进制字符串，`batch` 沿用 `RuleScheduleStatus` 字段名；其中 `TaskID`、`RootID`、`Revision`、`Sequence`、`ReleaseGeneration` 也输出十进制字符串，避免 JavaScript 超过 2^53 后丢失精度，`Total` 等成员计数仍为数字，Go 的 `RuleScheduleStatus` API 不变。未配置查询回调返回 404，阶段未注册为 `*RuleSchedule`、状态损坏或批次变化返回 409，查询超时返回 504。状态尚未分配首批时显示空批次，不假报完成；阶段不再注册的控制任务仍可在列表发现。自定义 Monitor 宿主可注入 `MonitorConfig.RuleSchedules` / `RuleScheduleDetail`；标准 App 自动连接 Engine。

本轮不新增表、配置项或依赖。使用周期批次仍要求此前的 `rules.enabled` 显式迁移，以及 `repeat_queue` / `recover_queue` 的正常配置。这里只展示当前批次，不提供历史批次浏览、强制跳过失败、历史清理或规则发布。JSON Meta 查询没有新增索引，大型历史库需评估查询成本；超时应缩小站点范围，不能无限放大读取预算。

### 轮询、错误提示与窄屏

监控请求完成后再安排下一次刷新（成功后 3 秒），失败逐步退避至 30 秒；请求及正文解析共用 10 秒期限。手动刷新淘汰旧请求，旧正文/错误/401 不能覆盖新状态或清除新凭据。隐藏页面暂停监控请求，回到页面恢复；401 停止定时刷新并显示登录。其他原生 API 保留服务端错误文案；写请求超时会说明结果尚未确认，不会自动重试。

`apiFetch/apiPost` 在同一 10 秒期限内完整读取响应正文，再向调用方返回 Response；正文超时或网络中断时释放操作锁，写请求提示先刷新核对结果。Trace、令牌写入和退出操作共用此处理；日志二进制下载保留独立读取路径，并在响应头和正文后检查登录代次。oao v1.3.4 的未授权回调不提供原请求凭据，因此表格 401 会合并验证当前凭据，只有当前凭据确实失效才清除登录，绝不自动重放写操作。重新登录验证成功后重新读取当前内置业务页面；旧菜单及旧 Trace 响应不覆盖新视图。

共享弹窗被新弹窗替换时，旧确认按取消完成，避免遗留等待和按钮锁。Tab/Shift+Tab 在弹窗内循环，Esc 取消；关闭后恢复仍存在的触发元素，取消批次确认后由批次页恢复被重绘替换的按钮焦点。

队列「立即执行」按队列防重复提交，并明确标注「全部站点」，顶部站点筛选不改变其作用范围。窄屏导航可通过「菜单」展开，选中模块后收起，桌面布局保持原样。

整值 URL 链接通过 oao 的 `table-loaded` 扩展点兼容 v1.3.4：`Href: "{url}"` 且显示列也是 url 时按 HTTP(S) 地址跳转；含路径/查询参数的模板继续保持参数编码。非法协议显示文本不提供跳转。适配只在 Papa 宿主页生效，未修改 oao 模块缓存或宣称修复其他宿主。

## 12. 运行概览

首页默认展示四项紧凑数字、最多三条关注事项、一张排队/未完成趋势图和站点列表。详细分析、阶段/Worker 明细、系统资源/目录分别放在默认折叠区域；站点控制仍使用原有暂停/恢复接口。

| 内容 | 含义与范围 |
| --- | --- |
| 排队中、未完成（含排队） | 活跃阶段内存队列与提交后尚未结束的任务；后者包含排队，两者不可相加，均非数据库任务总量 |
| 累计完成、累计失败 | 活跃阶段累计次数；阶段池生命周期会影响累计范围，不代表当前成功/失败记录存量，也不用于直接判定当前故障 |
| 需要关注 | 熔断暂停、队列上次执行错误、人工暂停和有时间戳的积压样本；队列停用按状态提示，不能单独认定为故障 |
| 队列积压 | 始终为全部站点，标注绝对采样时间；没有有效时间戳时显示尚未采样，不能据默认零判断无积压 |
| 站点概况 | 包含声明站点、阶段归属与暂停现场中的站点；没有活跃阶段仍保留站点入口，未提供暂停统计时显示未知 |
| 刷新状态 | 最后成功时间只在监控请求成功时更新；失败保留上次快照并明确标注，切换站点不会刷新这个时间 |

站点行的「阶段」选中本站、展开阶段明细并将键盘焦点放到明细标题；「任务」打开带本站筛选的任务表；「批次」打开本站周期批次。队列事项进入全局队列治理，不能把顶部所选站点当成队列动作范围。新入口只导航，操作保护与审计仍由原页面负责。

关注项最多显示三条；其余队列项进入「异常处理」，其余暂停项进入铃铛详情，避免遗漏全局暂停。事项按钮焦点在后续刷新中保留。未变化的数据块不重复替换 DOM。移动布局采用两列摘要、堆叠事项和局部横向滚动表格，沿用浅深色及自托管字体。

运行概览只复用 `/api/monitor`，不增加轮询、数据库查询、表、配置或依赖；没有持久趋势、跨重启累计或完整告警历史。自定义宿主需要照原接入约定注册任务表、周期批次回调，才能使用相应导航目标。规则发布管理见下一节。

## 13. 规则运维

标准 App 在 `rules.enabled: true` 时自动装配此页，要求已执行既有规则表迁移；普通启动不会迁移。版本库全局共享，按精确规则 ID 查询，每页 20 条，按 ID/版本字节顺序分页，不按版本号大小或站点推断归属。查看内容包含不可变规则、当前可用于发布的验收和最近 5 条验收记录。失败重验会撤销再次发布的资格，但保留曾发布版本的执行资格；「曾发布」不能代表某站点当前采用它。

操作顺序：选择或填写目标站点并读取发布 → 审阅版本/验收 → 填写完整阶段清单 → 预览差异、移除项和依据 → 勾选审阅确认 → 确认发布。可以先填入当前清单再修改版本：

```json
{"list":{"id":"catalog","version":"v2"},"detail":{"id":"detail","version":"v1"}}
```

完整清单遗漏的阶段会从该站点新发布中移除；它不会修改部署的 Fetcher、传输方式、Save 回调或阶段声明。发布只影响后续获取新快照的采集，已固定版本的任务和在途周期批次继续使用原发布。

回滚只能沿当前发布的前驱谱系逐次回退。预览显示实际目标及其历史验收依据；确认后创建新代次，不编辑原发布、不在两个版本之间自动来回切换。当前发布与历史页来自同一 MySQL Repeatable Read 只读快照；历史每页 20 条，大整数代次均作为字符串传输。

### 操作保护与恢复

- 沿用后台令牌/IP 白名单。发布/回滚额外要求鉴权得到非空操作人，未配置令牌时管理接口默认拒绝访问，不能匿名发布；没有新增角色权限。
- 发布事务在版本锁内核对预览的验收 ID；代次或验收依据改变时拒绝旧确认，必须刷新并重新审阅。失败不会替换当前发布。
- 浏览器先将已确认参数及随机 operation ID 存入当前标签页会话存储，再提交。刷新页面仍显示「待核对的人工操作」；先点「核对结果」，未找到不等于失败，也可能仍在处理，可显式重发同一 ID/参数。不会自动重发或换 ID。
- 网络/超时/未知提交结果、操作 ID 冲突或完整性错误保留恢复记录；服务端明确判定参数/代次/审核失效等事务拒绝后，才结束本次操作。确认成功也会清除记录。会话存储不可用时禁止开始写入。
- 会话存储仅覆盖当前浏览器标签页的重载恢复；关闭标签页、清理浏览器数据或使用另一个设备后，按发布历史或已记录 operation ID 核对，不能直接创建新 ID 猜测重试。
- 成功发布审计始终由规则仓库保存；尝试的成功/失败接入 `server.operation_log`。操作人来自鉴权上下文，来源固定 `oa`，请求体不能覆盖身份。

### API 与自定义宿主

| 方法/路径 | 用途 |
| --- | --- |
| GET `/api/rules/versions?id=&after_id=&after_version=` | 全局版本分页；游标是上一页末项 ID/版本 |
| GET `/api/rules/version?id=&version=` | 规则与当前验收、最近验收记录 |
| GET `/api/rules/verification?id=` | 指定固定验收报告，不读取样本正文 |
| GET `/api/rules/releases?site=&before=` | 当前发布及该代次之前的历史，首屏 before=0 |
| GET `/api/rules/operation?id=` | 按原 operation ID 核对已提交结果 |
| POST `/api/rules/preview` | 只读预览，参数为 kind、site、generation 字符串和发布 bindings |
| POST `/api/rules/change` | 人工提交，增加 operation_id；发布还须带按阶段固定的 verification_ids |

请求正文最多 64 KiB，严格拒绝未知字段与尾随 JSON，数据库请求期限 5 秒。原生客户端期限覆盖完整正文；不会因 401 自动重放写入。已知错误使用 400/403/404/409/504，原始数据库错误只进服务端日志。`X-Rule-Outcome: rejected` 只标记可确定未完成写入的拒绝，不把提交后读取异常归为已拒绝。

自定义 Monitor 在 `MonitorConfig.RuleAdmin` 注入 `rulestore.NewAdmin(db)` 的结果，必要时设置 `OnRuleChange` 记录尝试。此元数据门面不打开样本目录、不触发文件权限修改、不执行模型或网络采集。未接线明确返回未启用；质量报告查看见 §14，Agent 运行与候选审阅见 §15；规则编辑、样本导入和重新验收仍由现有 Go 接口负责。

## 14. 质量监控中心

「运行监控与报告 → 运行质量」提供观测查询、临时汇总、已有持久报告与证据/Trace 定位。标准 App 根据 `quality.enabled` 注入查询 Store；自定义 Monitor 显式设置 `QualityAdmin`。没有接线时明确提示未启用。采集观测仍需宿主给 RuleFetcher 设置 Collector，仅打开开关不会产生数据。

- 顶部站点与阶段/规则 ID/版本精确筛选，时间窗口 `[from, until)` 最多 7 天。本地时间输入转换成 RFC3339；「最近 24 小时」更新窗口终点后重新查询，普通重新查询保留用户指定时间。
- 列表显示候选数与匹配数，每页最多 50 条候选（额外读取 1 条判断后页），不显示推测的全站总数。过滤不匹配时允许继续扫描；数据库实际索引遍历不受 50 行限制，有 5 秒查询期限。现有表无站点索引，本批不新增表或迁移。
- 观测倒序键集分页固定序号上界，新增更高序号不会进入后页，但迟提交/保留期清理仍可改变可见记录；不是跨请求事务快照。报告按二进制 ID 倒序翻页，是实时列表；新增报告需重新查询。报告列表按报告创建时间过滤，不按其观测窗口过滤。
- 临时汇总从选定观测携带完整规则与发布范围，在独立一致性事务中读取窗口最早 1000 条，超过即标截断；使用 DefaultPolicy，无基线，不保存报告。策略、尝试/折叠页、完整评估页、字段分母、失败分类与信号分开展示。
- 无记录显示原因提示，不判定质量正常。「已记录范围内未见异常」也不代表覆盖全站或字段语义正确；未记录量未知。已有报告沿用生成时的策略、基线和失落数，不从当前 Collector 猜历史数据。
- 观测详情展示证据 ID/原始响应摘要；持久报告引用需与观测完整匹配，记录过期返回 404，完整性/关联错误返回 409。Trace 走既有 GET 接口，按任务展示并要求核对尝试编号；页面不直接读取任意证据文件，也不另存 HTML。

上述查询 API 全部 GET，沿用 Monitor 认证/白名单、`Cache-Control: no-store`，其它方法 405，错误不暴露 SQL/DSN。未知或重复参数、非法十进制和范围均拒绝。所有序号、截止值、发布代次与任务 ID 在 JSON 中以字符串输出，浏览器不得转为 Number。

| 路径 | 参数与结果 |
| --- | --- |
| `/api/quality/observations` | 必须 `from/until`；可选 `site/stage/rule_id/version`、后页 `before/cutoff`；返回 `items/scanned/cutoff/next`，`next="0"` 结束 |
| `/api/quality/reports` | 同上时间和可选过滤，后页用 `before_report`；返回 `items/scanned/next`，空 next 结束 |
| `/api/quality/observation` | 必须 `id`，可选 `report_id` 校验报告引用；返回完整无值观测 |
| `/api/quality/report` | 必须 `id`；返回持久报告，保留原观测窗口/策略/证据 |
| `/api/quality/summary` | 必须 `site/stage/rule_id/version/from/until`；传原 `release_id/release_generation`，未绑定时省略或为空/0；返回 `id=""` 的临时汇总 |

页面使用手动刷新；筛选修改、切站点、离开模块和重新登录会使旧请求失效，新查询先清除旧详情。错误保持在对应面板，不继续展示上一范围的统计。报告固化与显式复分析见 §15；没有自动发布、告警推送或权限角色配置。

## 15. Agent 运行与候选审阅中心

标准 App 在 `agent.enabled=true` 时提供运行审计查询。要从页面执行复分析，宿主还需启用并迁移 rules/quality，且在 `Run` 前调用 `App.UseAgentCenter(agentadmin.Options)` 注册批准配置。没有配置时仍可查询历史，执行入口明确显示未接线。本批复用现有表，不增加迁移、模型 YAML 字段或权限角色。

### 操作顺序

1. 在「质量监控」查看观测并生成临时汇总，核对窗口、范围、截断和覆盖后点击「固化当前汇总为报告」。服务端重新查询并比较输入摘要，变化返回 409；只接受查询与摘要，不接收浏览器计算的统计。固化沿用 DefaultPolicy、无基线、最多 1000 条、失落数量未知的已有覆盖语义。报告保存操作人和操作 ID，重复操作返回原报告；原观测被清理后仍可按操作 ID 查询。
2. 从持久报告进入「Agent 审阅」，选择宿主批准的配置和 1～8 个报告证据。预览显示实际默认值归一化后的目标、模型、访问限制、预算与独立样本集，以及 `Plan.HistoryEnabled` 对应的历史规则披露状态；启用后仍须宿主逐项授权，状态参与预览摘要及运行快照，不表示已经调用模型。只有 `suspected_rule_drift` 且当前发布仍匹配的报告可进入复分析；持久报告来自 Go API 时可以保留原策略及基线。
3. 勾选审阅，具名确认「创建待执行请求」。此步骤只固定请求 ID、RunID、报告与操作人，不调用模型。再次具名确认「启动当前待执行请求」才提交后台执行；服务端重算预览摘要，核对原请求 revision，数据库 CAS 决定唯一执行者。202 仅表示本机受理，请刷新原请求查看持久状态。
4. 页面、HTTP 超时或离开模块不会取消已受理任务。后台运行从受理起受预览的总时限控制，包含证据读取、导入和 Agent 调用；审计收尾另有既定短期限。可显式取消本机任务，尚未开始的请求可 CAS 撤回。每实例默认并发 1，可设 1～4；这不是跨实例总配额。重启只读查询，不自动接管运行；`active=false` 不能证明旧执行器已停止。
5. 查看运行步骤和最终候选，核对固定训练/独立验收、规则摘要、差异与影子报告。独立验收缺失/失败、报告和规则或样本集不匹配、当前最新验收变化都会阻止交接。步骤中未完成的候选引用仅供核查，不代表最终验收通过。
6. 「带入人工发布页」读取当前完整阶段清单，只替换候选对应阶段，保留其他阶段并带上当前代次。页面仍要求人工预览全部阶段、勾选审阅和确认发布；Agent 中心没有发布写接口。正式发布沿用 §13 的 generation、验收 ID 与 operation ID 检查。

规则报告与候选的训练/独立验收详情显示正样本/负样本总数，以及每个样本的类型、通过状态、结果行数和实际拒绝/执行失败分类；下方保留完整 JSON。旧报告缺少类型时按原正样本展示，不伪造新增验收结果。负样本单项通过不能替代整组正样本门槛；页面不提供修改样本预期或跳过人工发布的入口。

### 未确认结果与停机

报告固化和请求准备发送前，先把原操作与完整参数存入同标签页 `sessionStorage`；存储失败则不发送。刷新不会重发，只提供按原操作查询、人工重发同一准备请求。准备因旧摘要等条件无法完成时，先核对原操作，再为同一报告/配置重新预览，使用「按本次预览重试原准备」；保持原 operation ID，不创建替代标识，且不能用于已发送启动的未知结果。并发已有请求仍由持久幂等检查决定，冲突后查询原操作。

启动保存原 request/revision，不能因 404、超时或 500 创建替代执行。关闭标签页或跨设备后，可从持久列表查看原 pending 请求，重新读取原报告、选择配置、预览并确认启动；页面以该请求的 operation ID 重建本地恢复记录，不再次 Prepare。恢复记录尚关联其他操作时仍需先核对它。待执行请求可撤回，运行中的请求只有真实终态才能解除原操作恢复约束。切换请求、运行或候选详情时先清除旧操作对象，加载中的旧详情不能继续被启动或交接。

请求运行中但执行器确已停止时，宿主可注册 `WorkerStopped(ctx, request)`，必须证明**所有实例**的原执行者已经退出。检查应有界、遵守 context；本机 map 不存在、超时或页面确认都不足以证明。守卫与数据库 I/O 不占用中心全局锁；同请求恢复互斥，每实例恢复检查并发也受 MaxConcurrent 限制。Close 同时取消并等待分析任务和恢复检查，超时保留依赖，可再次等待；不响应取消的守卫返回后也不能继续补记。显式补记终态仍校验操作人、revision 和本机活动状态，只读取/中断原审计并关联原样本，不重放任何模型/网络动作。未注册该守卫时不提供此能力。

App 先停止 HTTP、取消并等待自己管理的 Agent 任务，再释放依赖；任务未排空时保留数据库/浏览器资源到进程退出。宿主拥有的模型、Repository 和 FileBlobs 应在 App.Run 返回后，再用 `App.CloseAgentCenter(ctx)` 确认任务完全停止才关闭；超时后可重复等待。自定义 Monitor 应自行调用 `Service.Close(ctx)` 并处理超时。

### 接口与接线

全部沿用认证、来源白名单和 no-store；管理请求 5 秒，写请求体最多 64 KiB，未知字段、重复 JSON 键、额外/重复查询参数拒绝。操作人只取具名令牌。revision、序号、发布代次保留十进制字符串。公开运行/步骤采用结构化白名单，不返回原 SnapshotJSON、输入、输出、凭据或完整模型回复。开启 operation_log 后记录固化、准备、启动、撤回、取消与补记尝试；实际执行终态仍以持久请求和运行审计为准。

## 业务设置扩展与页面生命周期

业务可以把控制台挂在同一后台，不必另启 HTTP 端口。`UsePage` 声明页面，`UseRouter` 挂 API（默认复用后台鉴权），`UseScript` 注册设置区。脚本与 CSS 是公开静态资源，不能嵌入密钥或私有配置。

```javascript
Papa.page('business-workbench', function (el, meta) {
    // 渲染页面、启动组件自己的轮询。
    return {
        beforeLeave: () => !hasDraft() || confirm('仍要离开未保存的草稿？'),
        destroy: () => { stopComponentPolling(); invalidatePendingResponses(); }
    };
});
Papa.settings('business-model', '模型配置', function (el) {
    // 使用 apiRequest 读取具名鉴权 API；返回同样的生命周期对象。
    return renderModelSettings(el);
});
```

`beforeLeave` 返回 false 会保留页面与输入；导航成功执行 destroy，清空旧容器。令牌失效直接强制清理，不能被草稿提示阻挡。旧 renderer 不返回值仍兼容，也可仅返回清理函数。异步返回值不属于 hooks 契约：renderer 应同步返回 hooks，内部自行启动异步加载；每个响应须检查组件是否已销毁。设置 label 使用文本输出，key 仅接受字母/数字/下划线/连字符。

同一根容器重新渲染时，先结束该容器的旧组件生命周期；其它根容器不受影响。清理回调若同步触发新页面渲染，新页面保留，外层旧导航停止；强制身份清理期间不接受旧组件重新挂载。请让 destroy 只释放本组件持有的资源，不操作新组件。

身份切换同时关闭原生确认框，清除令牌、设置、报告、批次、规则、质量和 Agent 页面的旧结果与审批状态。原身份晚到响应不更新新页面或解锁新操作。已发出的服务端写入不能通过离页撤销；sessionStorage 中的待确认操作记录继续保留，重新进入后按原操作 ID 人工核对，不自动重发或发布。

业务必须自行定义配置存储、权限和凭据管理；框架不保存供应商 Key，也不替业务启用付费操作。`apiRequest` 的 `current` 回调用于拒绝失效组件响应，写操作遇到未知响应不能自动重放。

在 `Run` 前注册 `app.UseShutdown(func(ctx context.Context) error {...})`，业务可在 HTTP 停止后、共享数据库/浏览器关闭前取消并等待后台任务。钩子按注册逆序执行，合计使用 crawler.stop_timeout。返回错误、panic 或超时会保留共享依赖，避免仍在收尾的 worker 写入已关闭的库；这不表示 worker 已结束。宿主回调应遵守 ctx，不应自行关闭 App.DB，也不要返回或记录凭据正文。

## 16. 图表、动效与本次页面观测

新版 oao 提供折线、柱形（含横向）、环形和迷你图。Papa 首页接入真实 `/api/monitor` 快照：排队与未完成趋势、当前站点的阶段排队分布、当前活跃阶段累计已结束结果、CPU/内存系统采样及根文件系统磁盘占用。

默认仅创建趋势图；展开「详细分析」再创建分布与结果图，展开「系统资源」再创建三张资源迷你图。折叠时销毁对应实例，离开概览时全部销毁。切换折叠不追加观测；后台标签页不新建图表，恢复可见使用缓存重绘。首次无数据、旧版 oao 无图表能力时不创建空图。

离开文档（pagehide）时挂起轮询并销毁图表，迟到回调不能重建。页面从浏览器缓存返回（pageshow）时先核对当前凭据，再恢复图表与轮询；凭据改变则清除旧观测，凭据删除则回到登录。KPI 节点替换或离页时取消旧动画，隐藏概览不播放新动画。站点表轮询保留横向滚动和操作按钮焦点。

- **未完成包含排队**：`in_progress = submitted - completed - failed`，不能将两条线相加，也不能把它称为准确的正在执行数。
- **时间范围是本页观测**：最近 10 分钟、最多 240 个已接受 HTTP 快照；图表最多 300 点（含断点）。刷新页面或切换凭据清空，同源其他标签页更换/删除凭据也会清空旧身份观测、作废旧请求并恢复轮询或回到登录。服务实例变化、时间倒退重置，长断线/阶段集合变化断线。没有数据库或 localStorage 历史，不是近24小时或跨重启统计。
- **切站点仅改变投影**：不会重复记录样本。阶段条形最多展示前 11 项和明确标注的「其他」，合并保留总计。结果环形只统计当前活跃阶段的完成/失败，不含排队，不代表全站历史成功率。
- **资源范围**：CPU/内存是当前运行环境的系统采样，不是 Papa 进程占用；容器中的可见范围由运行环境决定。磁盘使用 `disk.Usage("/")`，只表示 `/` 所在文件系统（Windows 当前盘根目录），不汇总全部磁盘。使用各自的成功采样时间去重；未成功采样、失败、过期与正常零值分别表达。成功采样后超过 `max(15秒, 3 × sample_interval_ms)` 判过期，时间比较在服务器时间域完成。首次失败而无成功时间显示「尚无成功采样」，不会冒充 0%。目录占用保留原有低频扫描。
- **治理队列不是资源采样**：积压以原 `backlog_at` 为准，不随每次 HTTP 刷新伪造采样时间。没有采样时显示未知。

`/api/monitor` 新增字段（原字段不删、不改含义）：

| 字段 | 含义 |
| --- | --- |
| `instance_id` | 当前 Monitor 实例的随机标识；实例内稳定，新建/重启变化 |
| `generated_at` | 本次响应组装完成时刻，UTC RFC3339Nano |
| `system.*_available` | CPU/内存/磁盘最近一次采样是否可用 |
| `system.*_sampled_at` | 对应指标最近成功采样时刻；无成功采样为 null，失败时可保留旧时间和旧数值 |
| `system.sample_interval_ms` | 实际系统采样间隔，用于判断样本过期 |

图表支持方向键逐点查看、Home/End、Esc 回入口、可展开数据表；标签按纯文本渲染。正常轮询保留焦点、数据表展开及横纵滚动位置，不连续播报每个数据点。设置页「显示与动效」支持跟随系统/减弱动效，偏好只保存在当前浏览器；存储受限时当前页仍生效。减弱模式关闭动画、过渡、平滑滚动及按钮悬停/按下的位移；数值立即展示真实值，不滚动虚构中间数值。

最后一个站点消失时自动回到全部站点，并刷新当前模块的筛选。WorkerPool 多个独立计数器读取期间出现的负值按未知处理，不钳制为零；阶段池回收的历史累计与旧统计移除在同一锁内完成，避免瞬时重复计数。目录配置与返回快照独立复制，调用方修改返回 map 不影响后续采样。

### 外观主题与明暗模式

进入「系统管理 → 系统设置 → 显示与动效」，可独立选择：

| 设置 | 可选值与默认 |
| --- | --- |
| 界面风格 | **简约（默认）**、经典；经典保留原来的粗边框、硬阴影和粗标题 |
| 明暗模式 | 浅色、深色；沿用已有偏好，新浏览器默认浅色，侧栏快捷按钮同步此项 |
| 动效偏好 | 跟随系统、减弱动效；两种外观均遵循减弱设置 |

两种风格共用四类导航与当前页面；切换仅改变外观，不重新挂载组件、不发送业务请求，也不触发规则发布。设置页尚未保存的模型字段、弹窗输入、表格筛选和图表展开保持。工作台切到设置页仍遵循正常草稿离页保护；若希望保留工作台草稿，可在另一同源标签页修改外观，当前工作台自动同步。

外观保存在本浏览器、当前站点来源的 `papa-appearance`，与 `papa-theme` 明暗偏好独立，不入数据库。首帧即恢复合法值，非法值回退简约/浅色。写入失败时本页选择仍生效，页面缓存恢复不撤销该选择；刷新或关闭后不保证保留。同源其它标签页的外观变更可同步，读取凭据被阻止时按未登录处理，不复用旧身份。

业务自定义CSS继续最后加载。需要统一外观的业务页面应在自己的作用域内使用宿主 `--background`、`--foreground`、`--card`、`--border-color`、`--border-width`、`--radius`、`--shadow-color`、`--font-display` 变量，并按 `html[data-appearance="classic"]` / `html[data-theme="dark"]` 扩展专属样式。框架不替业务全局覆盖硬编码颜色，也不需要修改oao发布资产。经典主题恢复视觉语言，保留新的导航结构，不是旧页面的逐像素复刻。

### oao 版本与部署

本批源码通过静态资源能力探测加载 `oao-charts.js/css`、`oao-motion.js/css`。Papa 当前依赖为已发布的 oao v1.4.0，包含图表、动效与完整表格生命周期，正常启用图表和表格行操作。兼容更旧依赖时仍按能力探测：缺少扩展则明确提示、隐藏空图容器，原生后台页面与表格查询可用，系统 reduced-motion CSS 仍生效。

新 oao 使用实例销毁与请求代次保护。旧 oao 缺少 `destroy` 时，Papa 提供**只读表格兼容**：页面显示升级提示，移除表格动作元数据，并仅通过宿主独立传输适配转发清单/分页 GET，拒绝该路径的非 GET；查询、筛选和分页保留。离开时关闭旧组件弹窗并替换旧容器，隔离迟到查询。

原因是旧组件的确认框挂在 body、动作回调按全局表 key 工作，仅移除表格节点仍可能在换身份后提交旧行，或让旧写入回调刷新新页。这不是修改服务端权限，也不限制 Papa 原生批次、规则发布或令牌管理；这些继续使用自己的保护流程。需要表格行操作时升级到具备完整生命周期保护的新 oao。已发送到服务端的写入不能靠销毁页面撤销，新版只抑制过期重试、Toast 和刷新等界面副作用。

升级部署：Papa 已固定到正式发布的 oao v1.4.0；业务若直接依赖 oao，也应更新到 v1.4.0 后重新构建、部署和重启 server。发布模块不加入 `replace ../oao`。可用 `GOWORK=off go list -m github.com/ydtg1993/oao` 检查实际依赖，避免 workspace 的本地源码掩盖发布产物。本次依赖升级不需要数据库迁移，不触发模型调用或规则发布。

本地合成演示：`go run ./cmd/monitor-demo -port 9091`，只监听 `127.0.0.1`，随机登录令牌输出在本机日志。阶段/业务为明确标注的合成数据，资源来自当前机器；不要把演示累计量当真实业务统计。

## 运行调度策略

开启 task_flow 后，「采集任务流」新增「运行调度策略」，按业务保存的运行 ID 查询。可分别调整各调度范围的广度/深度和并发上限，显式人工确认后应用到未执行任务；冲突保留编辑，刷新后重新决定。在途任务不中断，降低上限会等待旧任务收敛。该页不创建任务、不发布规则，详见 [动态阶段调度](TASK_FLOW.md)。数据与资源仍只展示任务及其 Trace 弹窗，不增加独立表菜单。


运行调度策略页沿用宿主的简约/经典与浅色/深色设置。输入运行 ID 后查询，尚未选择运行时显示引导；加载后再显示阶段策略与人工确认按钮。支持回车查询，空 ID 不发请求；窄屏控件改为单列，不改变策略确认和版本冲突规则。

## 模型设置

「系统管理 → 系统设置 → 模型设置」只显示五项：启用、HTTPS BaseURL、准确模型 ID、**API Key**、**每日 Token 额度**。直接在密码框填写实际 Key，不要求环境变量；默认每日 1,000,000（1M），统计输入与输出 Token 合计，可设 1～1,000,000,000。保存不调用模型，也不估算单价或费用。

Key 只写不读，保存后输入框清空；显示「已保存」时留空表示保留现有 Key。第一次启用必须填写 Key，旧环境变量配置需要在此重新录入。Key 使用 AES-GCM 加密存入 crawler_config，应用首次保存自动创建工作目录下的 `configs/.papa-model.key`。备份数据库时也需备份该文件；文件丢失/损坏时解密失败，不自动回退环境变量或覆盖旧文件。不要提交此文件；Windows 下还应由部署账户的目录 ACL 限制读取。宿主可用 `configstore.NewWithModelKeyFile(db, path)` 指定稳定位置，后台和分析入口必须使用同一路径。拥有数据库及主密钥文件的人可以解密，不能将此机制视为外部密钥托管。

每日额度由接入该配置存储的模型调用共享，不按分析任务、模型名、Key 或配置修订分别重置。按数据库 UTC 时间换算北京时间，00:00 切换到新一天；重启仍保留当天用量。调用前用输入序列化字节数、协议余量及输出上限预留额度，返回后按供应商 usage 结算；鉴权/限流等明确拒绝释放预留，超时/断线/未报告 usage 保留占用。页面展示已用与预留/待确认，崩溃遗留的预留不自动清除。跨日结束的调用归属开始时的日期。调小额度不会删除已用量或取消在途请求，后续调用检查最新额度；停用也阻止已创建 Provider 的后续调用。

预留是保守估算而非供应商精确 tokenizer，余额较小时可能提前停止；供应商报告超出预留的 usage 仍照实记账并阻止后续调用。因此这不是供应商账户级的精确账单硬封顶，也不统计其他应用直接调用同一 Key 的用量。内部单次输出上限（默认 4096）、超时、调用/候选数和字节边界继续保留，不要求普通用户编辑。旧价格字段兼容读取但归零；通用 Agent 自定义 Prices API 保留。

配置和每日用量复用 crawler_config（`agent_model`、`agent_model_usage:YYYY-MM-DD`），不新增表或迁移。宿主每次分析读取 `LoadModelSettings(ctx)`，使用 **`store.NewModelProvider(ctx, settings, network)`** 和 `settings.Budgets()` 构造 Agent；不要用裸 `model.New(settings.ProviderConfig(...))` 绕过已保存 Key 与日额度。模型/Key/单次预算按修订冻结，日额度和启用状态在每次调用前读取最新值；设置更新无需重启。原固定 Profile API 不被隐式替换。

`GET /api/settings/model` 返回公开配置、字符串 revision、key_configured 和 daily_usage；绝不返回明文或密文。`POST` 带完整配置和同一 revision，可加 write-only 的 api_key；不要回传 daily_usage。隐藏协议字段作为兼容 API 保留；CAS、具名鉴权、严格 JSON、8 KiB 限额保持。过期保存 409，非法输入/首次缺 Key 400，存储故障 503；断线或保存后用量查询失败时先重载确认，不自动重复提交。表单拒绝晚到响应覆盖编辑、阻止重复保存，身份切换清空草稿。
