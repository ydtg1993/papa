# Papa 任务恢复手册

> 面向：进程崩溃、暂停恢复或提交被取消后，继续执行已经接受的任务。
> 配套：[ERROR_QUEUE.md](./ERROR_QUEUE.md)（业务失败重试）、[FETCHER_WRITING_GUIDE.md](./FETCHER_WRITING_GUIDE.md) §1.6（投递契约）。

## 1. 正常投递与恢复的区别

正常投递是先持久化 pending，再等待对应站点、阶段的 channel 容量。队满时提交方阻塞，既不反复写任务行，也不把任务放入另一个内存积压列表。

暂停期间接受的任务、落库后提交被取消的任务，仍是 pending。框架通过阶段级唤醒通知恢复投递：按批读取未被本进程持有的 pending 任务，向有界 channel 发送。队满时扫描也等待，不每两秒重新查写同一批任务。数据库故障使用有退避的重试；通知可以合并，但不能丢掉投递责任。

内存仅维护正在投递、排队或执行任务的所有权，不维护与数据库积压等大的 Task 列表。投递恢复不改变业务终态，不消耗新的轮询代数。

## 2. 启动恢复

进程重启后，pending 需要继续投递，上一进程留下的 processing 需要条件释放回 pending。本进程正在执行的 processing 不能因耗时长被重新投递。不要用“超过若干小时”判断任务是否可恢复。

```yaml
recover_queue:
  batch_size: 100              # 每阶段读取批量，上限 1000
```

恢复是已接受任务的强制安全保障，不能关闭。每个已注册阶段独立恢复，队满时阻塞，不靠全局批间睡眠限速。`batch_size` 控制每阶段查询批量，运行期最多 1000 行。运行期 pending 投递恢复不是业务失败重试。

暂停的站点不执行任务，也不能阻塞其他站点的恢复。后台恢复整站或阶段会通知对应投递协程；阶段容量与 worker 数保持站点声明值。

## 3. 取消、关停与不丢任务

- `SubmitChildren` 返回错误不代表整批回滚：批量中已接受的任务仍持久化，由框架接管；未接受的项需要调用方处理。
- 停机先取消阻塞提交和恢复投递。尚未执行的任务保留 pending，在途任务按条件释放，已成功执行的正常落终态。
- 只有执行协程与持久化操作退出后才能关闭数据库。超时仍有在途操作时不得报告已经安全排空。
- 进程崩溃后允许重新尝试；业务写入仍需幂等，恢复不承诺外部副作用恰好一次。
- 任务身份、meta、加急和最早投递时间从数据库恢复。新增 `not_before` 列必须先执行 `papa migrate`；NULL 表示无延迟。普通启动不自动迁移。

## 4. 诊断

数据库 pending 不等于内存 channel 长度：暂停期间 pending 可以很多，但内存仍有界。判断积压应结合阶段暂停状态、队列深度、正在执行数量及数据库状态。

没有声明的阶段保留待处理记录；恢复阶段声明后才能执行，不能静默删除任务。业务失败终态由错误队列处理；投递容量不足不应被记成业务失败。

升级时同时新增 `idx_task_delivery(site, stage, status)`，支持按阶段读取 pending 的游标查询。InnoDB 二级索引包含主键，可承接同阶段状态下的 ID 顺序；实际执行计划仍以目标数据库 EXPLAIN 为准。大表迁移需预留建索引时间；不在普通启动中自动迁移。


## 2026-11-14 二次审查补充

- 恢复扫描遇到已有内存所有者的 pending 行时，在投递协调器锁内登记一次释放后复查；所有者释放后重新通知对应阶段。解决轮询/人工重投已落 pending、旧 worker 仍在回调或间隔等待时的唤醒丢失。普通完成不额外触发扫描。
- 空闲 worker 收到任务后再检查暂停闸门，覆盖“通过闸门后阻塞收任务”的时序窗口；停机仍解除闸门并按取消上下文排空。
- 空闲池回收通过 workerpool.StopIfIdle 原子检查并关闭入口，不能把检查之后刚接收任务的池从登记表移除。
- 批量带 ID 提交按 ID 回读后再次验证持久化 site/stage；自定义幂等键即使命中内存去重缓存也复核归属。同批同键跨站点或阶段直接报 ErrTaskFlow。
- 控制面入口和管理员 API 仍是受信任应用权限，不是恶意插件沙箱：业务若主动丢弃 handler context 并调用管理入口/直接写数据库，不在阶段图防误用保证内。正常 fetcher 必须使用 SubmitChildren。
- 已落库任务保证可恢复，不保证崩溃窗口内 HTTP/业务副作用恰好一次；暂停也不撤销已经开始执行的外部请求。
