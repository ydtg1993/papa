## 已确认目标

保留现有 Session、Cookie、账号管理器、多站点与多阶段架构，在单实例中增加：站点内账号池保持当前账号，账号失效时由独立调度器切换备用；失败任务由任务补偿机制处理，不等待切换；后台动态调整采集策略；按站点启停 AutoThrottle；跨阶段共享请求预算；可配置 CPU/内存压力控制和站点公平性；代理健康反馈。任务去重规则优先，不因更换账号重新创建同页面任务。新限制主要作用于新工作，在途任务正常完成。不恢复 Agent，不执行 Git 写操作。

## 方案选择

推荐采用共享策略与观测契约，加独立的账号选择器、请求控制器、资源放行器及代理健康管理。通过既有 Engine/客户端接入，不反向依赖业务代码。

替代方案一：所有逻辑写到业务 Fetcher。接入快，但多站点重复、难以统一限速和后台调节，不符合本次目标。

替代方案二：一个大调度器同时管理全部等待与生命周期。集中但耦合强、取消和资源互锁风险高，不推荐。

## 1. 账号池

分组键为站点+池名，成员引用现有 account.Key，不复制 Cookie 或认证状态。每站可有多个命名池，例如相同权限账号组成一个池；阶段或业务调用显式选择池，不能按站点把权限不同的账号混为可替换账号。

按用户补充，池内以哈希表维护成员索引，使用结构化的站点、池名和账号 ID 作为键，避免字符串拼接歧义。哈希表负责快速查找与失效标记，不以 Go map 的随机遍历顺序选择备用账号；替补顺序由独立的有序成员清单维护。不为此引入 Redis。账号有效性由站点+账号统一维护，同账号加入同站多个池时，各池均跳过其失效状态。

成员状态至少包括待验证、可用、失效、停用和冷却，记录原因类别、更新时间和状态版本。确认账号失效时立即移出可选集合并启动有界补偿，不等待每次选取时再次碰失败。失效标记及停用状态持久化，重启不得自动重置为可用；持久化失败时当前进程仍禁止新请求选中该账号，并明确报告状态未保存。重启恢复的账号须复验后才能参与选择。

用户同意分离状态职责：登录态及凭据版本由 `pkg/account` 管理；人工停用、补偿隔离、冷却、原因及管理状态版本由独立管理记录持久化。最终可选状态由认证状态与管理状态共同计算，池不得再保存第三份可用布尔值。HTTP 与浏览器的配置能力和验证状态分别判断，不能用 HTTPReady=false 排除仅支持浏览器的合法账号。当前 StoredState 仅保存凭据快照，不能代替管理状态存储；实施必须增加管理状态的加载/保存及启动复验接线。

失效账号通过 OA 的重新验证动作，或显式开启的定时复验机制，在现有账号恢复/检查成功后重新加入可选集合；冷却到期仅允许复验，不直接认定账号有效。重新可用不会使池自动切回该账号。管理状态版本、凭据版本及池选择版本共同保证并发失败只标记/切换一次，旧请求失败不能覆盖已重新验证的凭据版本。

账号池主要提供失效补偿，不按请求或任务正常轮换。首次绑定和故障替补按稳定成员顺序选择同站同池的可用账号，跳过暂停、冷却及需要人工验证的成员。当前账号仅因并发已满时等待其名额，不作为故障切换理由。没有可用替补时进入可取消等待并显示原因，不静默匿名访问、不忙循环。

用户最新澄清：任务执行与账号切换分别运行。账号正常时持续使用，不因任务完成、阶段变化、轮询或正常重试而切换。任务发现明确账号失效后结束本次执行，进入 failed 等待以后补偿，并通知站点账号调度器；不在 FetchHandler 内同步等待或换账号重试。账号级失败应跳过当前阶段的立即尝试重试，但仍允许既有错误队列或人工重投以后补偿。

调度器标记旧成员不可选，按备用顺序验证并选择新成员，原子发布当前账号及池选择版本。后续任务使用新选择。每次任务尝试内固定账号/凭据上下文，已发出的旧身份请求自然结束，不强制取消，也不等待所有旧任务排空后才发布新账号；旧任务需要继续发送请求时若发现选择版本已失效，则退出本次尝试，不混用新账号继续执行。任务错误与账号失效通知各自处理：同账号同版本的通知合并；状态持久化失败需重试并可观测，调度器不能只依赖可能丢失的内存通知，还须扫描已记录的待处理失效状态。

切换期间或无可用账号时，新任务在认领前等待账号就绪，不占全局执行配额；已经在途的任务按自身结果结束。普通网络超时、解析错误和整站限流不直接认定账号失败，单个 HTTP 403 不无条件触发换号。现有显式账号 API 的登录态恢复行为保持兼容；池接入入口需要区分正常认证与已明确失效后的请求重放，后者交由任务补偿，不隐式沿用 Manager.Do 的 GET/HEAD 自动重发。切换次数、验证次数和冷却时间均可配置，避免空转。

现有 `(site, stage, url_hash)` 与自定义幂等键规则保持最高优先级，不增加账号维度，不因切换而重新抓取已完成页面。重复提交返回既有任务，不覆盖其站点/池归属；同任务若被请求绑定至不同池，则明确返回归属冲突，不创建第二条任务。以后补偿复用原任务记录并在执行时取得池当前账号。账号专属游标或资源 ID 不自动迁移，由业务判断是否支持安全补偿；不支持时暂停该任务并给出原因。

已指定账号的旧 API 保持可用。账号轮换不能自动重放已经发出的有副作用请求。身份失败允许结束当前尝试，但是否更换账号重试须服从业务幂等规则。权限不足不直接当成代理失败。认证等待与账号许可**复用 `pkg/account` 的 `MaxConcurrent` 名额与单飞（flight）**，池层不另设账号许可，避免重复计数、自身嵌套申请造成死锁；所有释放路径覆盖错误、取消和 panic。

### 已确认的持久化简化方案

采用“每站每池当前账号”，无需每条采集流程单独绑定：建议撤销此前新增 crawler_account_flows 表的方案。保存池成员/顺序、池当前账号与选择版本，以及账号管理状态；任务只保存或确定性解析所属池，实际使用账号与版本作为尝试记录，不作为永久执行绑定。不复用 TaskFlow 字段，不要求开启 TaskFlow。

第 4 项复审问题的例子：任务 T1 使用账号 A 失败，若 T1 指向的流程绑定 F1 被当作“流程结束”删除，次日重投 T1 会找不到 F1。上述简化方案让 T1 次日直接查询所属池当前可用账号 B，不再依赖 F1，因此不需要为了补偿永久保留流程绑定。池本身仍不能在有待处理、失败可重投或轮询任务引用时直接删除；应先停用，显示引用任务，显式处理引用后才能删除。账号使用记录与切换日志按保留期清理，不影响任务重新取得当前账号。

密码、Cookie、Token、登录实现仍由业务注册及现有凭据存储管理，不进入普通运行策略 JSON。池运行状态与账号管理状态使用明确的持久化模型，不混入 sites 快照；具体表与迁移在该简化方案确认后的实施计划中确定。

新增"数据与资源 → 账号池"，不是只有运行策略中的一个数量指标。当前代码尚未提供该通用管理页，本次新增。

- 按站点筛选池，展示当前账号、总成员、可用/失效/停用/冷却数量、等待任务数、最近切换时间与原因。
- 池详情展示账号 ID/备注、HTTP/浏览器验证状态、并发使用数/上限、最近检查时间、失败类别、冷却时间及管理状态版本；当前账号按站点+池区分。

## 2. 配置与后台热调整

新增 YAML 运行治理配置，包含全局默认和按已注册站点键的覆盖。原 Go 声明保留站点/阶段结构和默认参数。生效优先级：框架默认 → Go 声明默认 → YAML 显式覆盖 → 后台持久覆盖（Go 声明与 YAML 冲突时 YAML 显式优先）。YAML 中只有显式提供的字段参与覆盖，false/0 与未提供必须区分。

复用 crawler_config 表，但注册独立的运行策略键，JSON 值包含 schema_version、全局策略和站点覆盖。revision 只以表列为权威来源，通过 API 单独返回，不在 JSON 值内重复存储。sites 继续只保存快照。后台可以清除覆盖，回到文件/声明值；重启恢复覆盖，不用新声明覆盖后台选择。运行策略本身不增加凭据列、不加新表；账号与池的运行状态另按 §1 设计。

写入流程：校验站点与参数 → 检查 revision → 持久化 → 原子发布不可变策略快照。单实例内串行配置变更，旧 revision 返回冲突。数据库失败不发布；提交回执不明确时重新读取核对，不自动重放写入。启动读取失败或已存策略非法时明确阻止启用采集，不静默退回更宽松策略。

revision CAS 的落点：当前 `crawler_config` 只有 cfg_key/cfg_val/updated_by/updated_at，`Save` 是盲 Upsert，做不了「旧 revision 冲突」。裁决：**给 `crawler_config` 加 `revision` 列（一次显式 `papa migrate`），写入改条件更新 `WHERE cfg_key=? AND revision=?` 自增**，复用 `crawler_task_flows` 的 revision 先例；不在 JSON 里比整块 cfg_val。

新增专用 LoadVersioned/SaveCAS 入口；旧 Save 保留对白名单、sites 的兼容行为，但明确拒绝写入受 CAS 保护的新策略键。新键不存在时 API 返回 revision=0；首次提交使用唯一键保护的 INSERT 写入 revision=1，并发首次创建的失败方返回 409，不覆盖赢家。已有行使用条件更新并递增 revision。恢复默认也通过版本化写入清空覆盖，保留版本序列，避免删除重建导致旧 revision 再次匹配。

可热调：阶段有效执行并发、任务间隔、站点请求并发与速率、AutoThrottle 参数、资源阈值、站点权重、账号池选择和代理健康参数。物理 worker/浏览器池容量、队列容量、数据库连接、站点拓扑和凭据来源仍是启动配置；后台明确显示容量上限。降低限额等待在途收敛，不能中断已有任务。

新功能缺省关闭，旧配置保持行为；显式开启后必须满足参数校验。各控制器独立开关，关闭 AutoThrottle 仅停止自适应调节，仍遵守用户配置的硬限速。

后台配置入口统一为“运行监控与报告 → 采集控制”，与实时状态在同一页核对；不再另设一份独立“系统管理 → 运行策略”编辑器。页面提供全局/站点配置、保存与恢复默认，展示配置值、生效值、revision、等待原因、最近调节时间、资源采样有效性和账号池可用数。沿用令牌鉴权、操作日志、严格有界 JSON 及前端请求代次保护。审计不包含凭据和完整代理 URL。

## 3. 跨阶段请求预算与 AutoThrottle

同站目录、详情和内容共享请求控制器。配置包括 enabled、max_inflight、requests_per_second、burst，以及 autothrottle.enabled、min_delay、max_delay、target_concurrency、smoothing。多账户不绕过站点硬上限；关闭某站自动调节不影响其他站点。

采样使用实际 HTTP 交换的响应延迟，排除本地许可等待、账号认证等待和解析时间。成功响应参与平滑调整，失败响应不得导致加速；重定向和重试重新经过请求许可。既有任务 Delay 是任务节奏，与请求间隔分别展示，避免用户误认为二者等价。

429/Retry-After 支持秒数及 HTTP 日期，有配置的最大等待上限。有效响应触发站点/目标范围冷却，不由每个 worker 独立睡眠制造洪峰。503 的 Retry-After 同样受限处理；仅有 403 不自动判定代理不可用。响应到达后更新冷却状态，但不替业务重放 POST。

HTTP/HTML/账号请求应在共享传输边界计量，绕开框架客户端的业务请求明确不受控。**账号请求走 `account.Manager` 注入的 `m.client.Do`、不经过引擎请求路径 —— 给 account 客户端加计量/限速拦截器（或让请求控制器接管它）是接线方案，不是验证项**。浏览器主导航与受管网络请求需要经既有出口/CDP 接线；页面子资源、XHR、重定向的覆盖范围必须通过真实浏览器测试验证，不能只限一次页面打开就宣称全请求限速。CDN/第三方子资源按显式目标范围分类，不把其延迟盲目计入目标站 AutoThrottle。文件与 M3U8 的清单/分段请求也需接入同一站点预算；连接建立、分段并发和下载带宽分别计量。

OA 页面的布局、字段与操作约定见 §6。

## 4. 单实例资源预算与公平性

全局可配置：enabled、采样间隔、CPU 高/恢复阈值、连续高负载窗口、内存高/恢复阈值与最低可用字节、下降比例、恢复步长/间隔、任务/浏览器许可上限。阈值必须区分触发和恢复，形成滞回，防止反复升降。

CPU 持续高负载时降低可配置资源类别的新工作许可；内存紧张时优先减少新浏览器工作放行。浏览器许可在实际借用浏览器时申请，纯 HTTP 任务不消耗浏览器名额。资源闸门统一覆盖 Get、GetDirect 及其回调包装路径，包括账号专用池；获取失败、取消和归还均释放执行许可。存活实例数与正在借用数分别计量，不能用 alive 计数代替执行并发。池尚无可用容量时不得长期占住全局许可；采用可取消的联合放行或回退释放机制，避免某个专用池排队阻塞其他就绪站点。动态限额不超过物理容量，不杀浏览器、不强停任务。

各站配置 weight 与最小服务权重，按就绪站点轮转并允许空闲份额被借用。"最低服务机会"表示资源可用时避免饥饿，不是无条件保留 N 个同时执行位。全局内存紧急保护、站点暂停、账号不可用和远端冷却优先；不能为公平性突破安全总量。只有一个许可时，多个站点按完成后的机会轮流服务。

资源数据包括来源范围、采样时间和有效性。容器优先使用有效限制；无法取得数据时不把零当健康，保持保守限额并暂停自动上调。控制器使用独立可注入采样器，不依赖后台页面是否打开。

任务许可尽量在认领前取得；尚未获得许可的任务保持 pending。账号等待、站点冷却和资源等待不应长期占住全局执行配额；集中约定获取顺序和取消释放，验收专门覆盖交叉等待。不允许在持有数据库事务、引擎全局锁时等待许可。

## 5. 代理健康反馈

代理选择返回可反馈的引用，避免响应结束后丢失实际代理身份。配置 enabled、失败阈值、冷却初值/最大值、半开探测数、恢复成功阈值，状态至少包括可用、冷却、探测。

健康应区分代理连通性与站点范围拦截：连接失败/代理认证失败处理代理本身；站点 429 先处理站点预算；账号过期不污染代理健康。业务可通过受控分类回调报告已识别的拦截。代理列表刷新与状态合并，移除代理排空在途引用后回收；状态数量有界。

账号显式固定的代理不被悄悄更换。失效时暂停该成员，由站点账号池选其他可替换成员；浏览器实例的代理在创建时绑定，不修改在途实例出口。全部代理不可用时显示原因并等待，配置要求代理的请求不能退回直连。

## 6. OA 页面方案（已确认）

### 导航与分工

- 数据与资源 → 账号池：维护账号成员、启停、重新验证、备用顺序，查看当前账号和切换历史。
- 运行监控与报告 → 采集控制：三个页签“站点请求”“资源控制”“代理健康”。既有运行概览仍做总体摘要，跳转此页查看与调整。不在两个入口复制同一套配置表单。

### 站点请求

默认打开此页签。顶部提供站点筛选、名称搜索和状态筛选；全部站点视图只展示表格，不隐式将“全部站点”当成批量编辑范围。

| 站点 | 状态 | 控制模式 | 实际请求/秒 | 在途/当前上限 | 有效间隔 | 冷却剩余 | 等待任务 | 操作 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| example-a | 正常 | 自动 | 采样值 | 当前值/上限 | 当前值 | — | 当前值 | 查看 / 调整 |
| example-b | 远端限流 | 手动 | 采样值 | 当前值/上限 | 当前值 | 剩余时间 | 当前值 | 查看 / 调整 |

此表仅为布局示意，没有采样时显示“未采样”，禁止用示例值或默认 0 伪装实时结果。状态明确区分运行、用户暂停、远端冷却、等待账号、资源受限；多个原因同时存在时允许展开查看。

点击“查看”打开站点详情：最近窗口请求速率、响应延迟、错误/429 数量；各阶段使用量；最近调节原因及时间；请求类型覆盖范围。请求数与任务数分开命名。刷新不覆盖输入，不因打开页面触发请求采集。

点击“调整”打开右侧抽屉：

| 区块 | 可编辑项 | 说明 |
| --- | --- | --- |
| 站点硬限制 | 最大请求并发、每秒速率、突发额度 | 跨阶段、跨账号共享，自动模式也不能突破 |
| 控制模式 | 手动 / AutoThrottle | 手动使用指定请求间隔；自动在上下限内调节 |
| 自动参数 | 最小/最大间隔、目标并发、平滑参数 | 自动模式展开；关闭自动后使用明确配置的手动值 |
| 远端限流 | 缺失 Retry-After 时的冷却时间、最大自动等待 | 超出自动等待预算进入需处理状态，不提前重发以绕过服务端等待 |
| 阶段执行 | 有效执行并发、任务间隔 | 与站点请求并发/间隔分开，显示物理容量上限 |

各项同时显示“文件/声明默认值、后台覆盖值、当前生效值、来源”；自动计算值只读。按钮为“保存并生效”“清除本项覆盖”“取消”。清除覆盖后回到下层默认值，保存前展示变更差异。禁用自动调节不解除硬限额、远端冷却或全局资源保护。

有效并发是物理容量、用户限制、资源控制等约束共同允许的结果；固定每秒速率与自动间隔分别执行，页面展示实际限制原因。降低上限只限制新请求，允许当前在途暂时高于新值，并显示“等待在途收敛”。

### 资源控制

此页签始终为全局范围，明确标注“影响本进程所有站点”，不保留一个会误导用户的单站点筛选。顶部展示 CPU、内存、可用内存、采样来源/时间，以及资源控制是否开启；采样失效显示未知及当前保守策略。

中部展示任务执行、浏览器借用两类当前限额、使用数和最近调节原因；存活浏览器数量单独显示。底部展示各站点权重、等待数、当前获配执行数及最近获得服务时间。

“调整全局策略”抽屉包含自动资源控制开关、CPU 触发/恢复阈值、持续窗口、内存触发/恢复阈值及可用内存下限、任务/浏览器上限、下降比例、恢复步长/间隔、采样间隔。站点权重从对应行调整。说明最低服务机会不保证在内存紧急或远端冷却时仍强制执行。

### 代理健康

展示脱敏代理标识、健康状态、适用站点范围、连续失败次数、冷却剩余、最近探测结果、在途使用量与固定账号引用数。

支持停用、启用参与探测、请求一次受限探测，以及调整阈值/冷却策略；启用不等于直接标记健康，验证成功后才恢复候选。账号固定代理不可用时提供关联账号池链接，不在此强制改写在途浏览器代理。展示健康历史与配置操作记录，代理凭据不出现在表格或日志中。

### 账号池详情

池列表展示站点、池名、当前账号、可用/总数、池状态、等待任务数、最近切换原因。池详情分为“成员”“切换记录”“池设置”，不再提供逐采集流程绑定页面。

成员行提供停用、重新验证、加入/移出池及顺序调整；池设置包含备用顺序、验证次数、切换预算和冷却参数。切换记录关联触发任务但不自动重投该任务；失败补偿仍从任务/队列入口操作。后台查询均为只读，验证操作显式触发并展示进度和结果。

### 编辑一致性与验收

轮询仅更新读数，不覆盖未保存草稿。保存携带 revision；遇到 409 保留输入，展示最新值与冲突字段，用户重新决定。写入超时显示“结果待核对”，查询服务端版本和实际值后才能重试，不乐观显示成功或自动重放。未保存离页提示、身份变化清理旧页面、窄屏抽屉转整页。默认不提供批量修改、强制绕过限速和一键恢复所有失效账号。

页面验收覆盖：手动/自动切换、关闭 AutoThrottle 仍保留硬限制、429 冷却展示、资源降额后的在途收敛、账号耗尽原因、CAS 冲突与超时核对、未采样/陈旧采样、权限及脱敏、窄屏与键盘操作。关闭整个站点请求控制则关闭该控制器的请求限制；全局资源控制独立生效。

## 交付顺序与验收

1. 策略契约、持久化和后台编辑：CAS 冲突、重启恢复、恢复默认、写失败与新配置兼容。
2. 站点账号池与 OA 页面：站点隔离、多池、正常使用不轮换、失效任务结束且不等待切换、调度器独立切换、失败通知合并/重启恢复、重新验证后恢复但不自动切回、同账号跨池失效一致、普通失败不换号、补偿上限、旧响应隔离、去重优先、补偿复用任务且使用当前账号、账号并发上限及取消释放；页面查询不触发认证，管理操作鉴权/审计与在途移除保护。
3. 请求预算与 AutoThrottle：虚拟时间测试限速/平滑/冷却；本地 HTTP 测重定向、429、503、日期 Retry-After、非幂等请求不自动重放；真实 Chromium 测导航/XHR/子资源覆盖。
4. 资源放行与公平性：模拟 CPU/内存负载、阈值滞回、缩容不杀在途、单许可多站无饥饿、无效采样、与账号/请求等待组合无死锁。
5. 代理反馈：坏代理冷却、单次探测、恢复、站点与账号错误隔离、列表更新不丢在途引用、代理耗尽不直连。
6. 综合验证：本地合成多站、多账号、HTTP/Rod/下载任务；重启后策略一致；定向 race、Go 全量测试/vet/build、CLI 新建项目校验、真实 MySQL 配置并发写验证。环境未覆盖的验证明确列出。

每一步交付可独立验证的功能，后续步骤完成前不宣称整体自动治理已完成。文档同步 CORE_CONFIG、ACCOUNT_RUNTIME、FETCHER_WRITING_GUIDE、MONITOR、DEVELOPMENT、CLI 及配置模板；不写真实站点接线，不自动启动业务采集。
