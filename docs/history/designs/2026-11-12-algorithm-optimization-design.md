# Papa v4 算法优化方案（2026-11-14 修订）

> 适用版本：当前 Papa v4。原提案日期 2026-11-12；本轮按源码复审修订。
> 第一阶段退避优化已实施并通过其全仓/race 验证（门控跳过见报告）；CPU EWMA、自适应 α、repeat 缓存已完成本地合成评估，暂不落地。repeat 单语句查询优化已落实（实测与边界见 §10）；PID 不纳入当前计划。
> 当前用法见 [Fetcher 手册](../../guides/FETCHER_WRITING_GUIDE.md)，验证记录见 [退避实施报告](../reviews/2026-11-14-retry-backoff.md)。

## 1. 范围和边界

单实例内优化重试等待，不改变任务状态机、终态、认领版本、幂等、熔断、账号、重试次数或资源准入。保留公开 API 和字段；不新增 YAML 配置、数据库结构、后台控制入口或 obs 控制回路。其余算法不随本轮上线。

## 2. 本次修改前的代码基线与原提案修正

- Engine Handler 使用指数退避，无独立上限；filedown、M3U8 请求级和分片级已经各有 10 秒上限，原提案称后三者大多无封顶不准确。
- 下载的旧计算先移位/乘法再截断，极大参数可能在截断之前溢出。
- AutoThrottle 已有快速限流退避、Retry-After 与超预算暂停；固定 EMA 只是一部分，不能再用“429 只能慢慢 EMA 收敛”作为改造依据。
- repeat 节拍来自 next_repeat_at，不是 pending 延迟时间；自动最短 10 秒，wake 合并 250 毫秒。repeat 先对终态行进行有版本条件的轮次/状态/排期更新，再提交 pending。
- CPU 已是两次采样间的利用率，已有连续窗口、滞回、恢复间隔及无效采样保护。

## 3. 第一阶段：有界指数退避和 Equal Jitter

### 3.1 参数与行为

令 E = min(cap, base × 2^exponent)，必须在计算前保护溢出。
实际等待在 [ceil(E/2), E] 纳秒整数区间均匀采样（Equal Jitter）。

| 调用点 | 第一次重试 exponent | base | cap |
| --- | --- | --- | --- |
| Engine Handler | 0 | StageConfig.Backoff | 60 秒 |
| filedown 分片 | 1 | RetryInterval 秒；<=0 使用 1 秒 | 10 秒 |
| M3U8 请求级 | 0 | RetryInterval 秒；<=0 使用 2 秒 | 10 秒 |
| M3U8 加密分片外层 | 1 | 1 秒 | 10 秒 |

首次执行不等待，最终失败后不额外等待；MaxAttempts 含首次，MaxRetries 不含首次。Engine 直接 API 的非正 Backoff 保留立即等待完成行为；声明层继续要求合法正时长。整型秒到 Duration 的转换也必须饱和，不能先乘 time.Second 再保护。

此轮明确改变等待分布：Equal Jitter 平均约为 E 的 3/4，可能缩短重试周期；Engine 过去超过 60 秒的等待被封顶。它不是请求总数限额，不承诺降低总请求量。保留现有治理层的 Retry-After、速率/并发保护。M3U8 请求与加密分片的嵌套重试次数不变，非加密流式分片仍走请求级重试。

不增加 none/full/decorrelated 模式和可变全局随机源；避免为当前需求增加配置与跨调用状态。

### 3.2 职责与状态

- internal/backoff：仅标准库；负责安全秒转换、有界指数计算及抖动。无业务依赖、无 goroutine、无 context/Sleep、无重试状态或锁。生产使用并发安全的 math/rand/v2 顶层采样；测试通过私有纯函数参数确定采样边界，不修改全局随机源。
- engine/retry_backoff.go：拥有 Handler 60 秒策略及 attempt 到 exponent 的换算。
- pkg/middleware/filedown/retry_backoff.go：拥有分片默认基数、10 秒策略。
- pkg/middleware/m3u8/retry_backoff.go：拥有请求/分片两种 attempt 口径与 10 秒策略。
- 各原执行循环继续拥有取消等待、重试计数、事务、HTTP 请求及资源释放；不移动到公共工具组件。

### 3.3 不变契约

Engine 顺序仍为：等待 → incrementExecutionRetry 确认 → 发出 retry 事件 → 执行下一次尝试。确认失败不得再发请求或重复增加计数。等待取消时释放认领回 pending，不伪造 failed。没有新增锁、后台计时器服务或关停等待组；原 select(ctx.Done, timer) 保持。共享组件不绕过调用方取消和治理准入。

### 3.4 验证

- 极大 base、秒数、exponent，非正输入，1ns 与 MaxInt64 边界；计算始终有界、无溢出且工作量有界。
- 确定随机源覆盖抖动端点；固定序列验证分散；并发调用 race。
- 四处策略的第一次重试、指数推进、封顶和范围。
- Engine 成功前两次失败：三次 Handler、两次重试计数、一次认领、一次成功；等待取消/Stop 不增加重试、不产生终态、不遗留执行循环。
- 本地 HTTP 下载失败重试的次数、取消及文件清理；保留嵌套重试契约。
- 最终运行 go test ./...、go test -race ./...、go vet ./...、go build ./...。门控环境跳过单独统计；不连接业务库。

## 4. 已评估：CPU EWMA 暂不落地

责任包为 `pkg/governance`，不由 obs 驱动执行。当前区间采样已有连续窗口、滞回和恢复间隔。合成回放中持续过载首次缩容为 6s；叠加 EWMA α=.2/.5 后分别变为 20s/10s。孤立尖峰和阈值噪声三者都无调整，未显示新增滤波收益。

闭环离散负载模型里 α=.2 将积压峰值从 1,522 降至 1,456，但原始高 CPU 暴露从 3 tick 增至 9 tick，调整次数相同。模型不是真实 OS 满载，也不能以积压略降单独判优。当前先保留已有窗口；未来只有出现真实噪声导致错误调整的证据才重新评估。届时必须覆盖首次有效值、无效/过期/乱序输入、间隔和作用域切换，内存保护不平滑。

## 5. 已评估：AutoThrottle 保留固定 α

责任包为 `pkg/governance`，保留当前限流快速退避、Retry-After、超预算暂停和普通反馈 EMA。生产路径合成回放比较固定 α=.5 与测试侧“增加 delay 用 .8、恢复用 .2”：5 次快 429 后都为 3.2s，没有增强已有快速退避；恢复至 110ms 需要 9 次/26 次成功。5 次慢 503 后分别为 7.753s/7.997s，恢复需要 10 次/30 次成功。

控制路径微基准没有显示必须用自适应 α 解决的计算瓶颈；更慢恢复是否值得，仍需实际服务端负载证据。因此不添加错误窗口或自适应状态，保留现有可配置 Smoothing。累计 errors/limited 不是滑窗错误率，请求桶也没有同口径反馈分母。候选仅在测试中；不能把 delay 恢复等同于 cooldown 或 RemotePaused 解除。PID 不纳入计划。

## 6. repeat 单语句查询已落实，不引入缓存

`engine/repeat_schedule_query.go` 拥有最早排期查询构造，`engine/repeatpoll.go` 拥有执行/节拍，`internal/taskstore.AdvanceRepeat` 拥有原子轮次更新。使用本地 MySQL 8.1.0、新建随机测试库，测 1k/10k/100k 行、稀疏/稠密/未排期分布及 16 个阶段上限；两轮均清理完成。

已复现实际瓶颈：100k 可轮询行的最早时间聚合读取约 100k 次，p50 约 44–45ms；附加 16 个 RepeatLimit 后约 225–342ms。现有索引覆盖不等于聚合能跳过全范围扫描。空闲时查询频度很低；持续 wake 时约 250ms 的合并窗口会放大成本，不能以此宣称所有部署均有瓶颈。

前轮四次读取原型与随后单语句 UNION 有序候选都已撤销。复审实库证明：[1971, 2038) 内也能存入零月/零日、2 月 30 日等非法日期，UNIX_TIMESTAMP 可返回 0，按 DATETIME 取首条不等价；调用方排序/分页也会被候选 LIMIT 改写。当前使用一条过滤聚合 SQL：`repeatable = 1 AND (status IN (success, failed) OR next_repeat_at > NOW())`，加原阶段上限后，计算 `MIN(CAST(UNIX_TIMESTAMP(COALESCE(next_repeat_at, NOW())) AS SIGNED))`。这是把 CASE 的非 NULL 分支条件下推到 WHERE，保留未知/NULL 状态、非法日期、单语句 NOW 和调用方作用域。不修改写路径、结构、索引或 API。性能须按当前查询重新测量；旧有序探测的大幅加速数值不代表当前实现。

暂不建立时间堆/近期候选缓存。wake 无 ID，保守全失效时在持续写入中收益有限；保留缓存又要证明失效、容量、陈旧项、周期校准、重启及取消契约。只有查询优化后仍有明确成本、且命中与正确性收益实测成立时再评估。DB 继续为权威，保留阶段 RepeatLimit、补偿/熔断限制、强制轮询和关停排空。

## 7. 验收边界

本轮正确性/race 测试不证明生产吞吐收益；真实故障洪峰、24/72 小时运行和不同服务端限流策略仍需业务侧独立验收。框架只使用通用合成任务和本地 HTTP fixture，不访问业务数据。

## 8. 第一阶段复审补充（2026-11-14）

本次复审未发现退避计算或四处策略接线错误；修复 Engine retry 写入入口的取消边界，并补强验证证据，不增加配置或改变等待分布。

- 秒转换在最后一个可表示整秒的前/当/后点校验，并用任意精度整数作为独立指数计算参照；计算包额外运行 Windows 386 测试，不能据此宣称全框架 32 位验收。
- 抖动必须在生产 `Delay` 入口和四处策略入口均呈现不同值；只断言范围会放过“固定返回 cap/中点”。私有采样函数继续用固定种子和端点验证。
- 取消/期限测试使用标准库 testing/synctest 虚拟时间。确认 Handler 收尾时间已写、或内存 HTTP 响应已关闭，再等待其它 goroutine 稳定阻塞；不再用请求到达后睡 100ms 作为已进入退避的证据。真实本地 HTTP 次数测试仍保留。
- 实际执行循环验证首次不等待、两次间隔落在策略范围、最后失败后不空等；不是只测 helper。
- 退避 timer 与 Done 同时就绪可能选择 timer。`incrementExecutionRetry` 入口若已观察到取消，尚未发起增量写，须释放认领并返回取消，不增加内存 retry、不标未确认；进入写入后才发生的取消仍保守记未确认，不回退、不重复加法。
- Stop 首次返回与 worker 生命周期分别断言：fake COUNT 显式为 1，预期 worker stop 事件一次、无执行中/驻留引用，但整体 drained=false、Queued=1。假驱动不执行 SQL，这不是实库状态转换证明。
- 断言失败也取消执行、收拢 goroutine，并关闭测试事件转发器。临时 Go overlay 注入固定退避、忽略取消、错误 drained，要求新测试因断言失败而拒绝这些变体。

## 10. Repeat 单语句实施（2026-11-14）

执行绑定 Engine context；预取消不发 SQL，查询返回后再检查取消。沿用 tickerWG/Stop 排空，不新增锁或常驻状态。隔离 MySQL 以冻结 NOW 对照原聚合，覆盖终态 NULL 与过去值竞争、NOW±1ms、四状态/未知/NULL、阶段上限边界、同名跨站、调用方范围、极端日期及 SYSTEM/+00:00/+08:00；并发事务翻转和 RC/RR 验证同语句一致视图。真实元数据锁验证取消，拒绝取消的测试边界验证 Stop 不能假报排空。

复审增加非法日期混合集、调用方查询作用域和更强的独立预期；并发有/无上限各 300 次读取，每 100 次要求写事务实际交错。规模矩阵增加 99% 活跃过期行，区分过滤收益与仍需扫描的稠密未来/全部被上限排除分布，不宣称普遍加速。当前结论见 [repeat 查询复审报告](../reviews/2026-11-14-repeat-query-rereview.md)；[首次实施报告](../reviews/2026-11-14-repeat-query.md) 保留为已撤销快速路径的历史证据。CPU EWMA、自适应 α 和缓存的暂不落地结论不变。

## 11. 全达上限的成本复核与条件合并（2026-11-14）

先在独立测试库比较原 CASE、当前过滤聚合、交换 WHERE 次序，再用语句级 NO_ICP 作为诊断。全为未来排期且已达上限的 100k 夹具中，当前状态/时间谓词被 ICP 下推，但没有排除任何索引候选；全部行回表后才由上限排除，聚合输入为 0。交换 SQL 条件顺序没有稳定收益；强制禁止 ICP 会破坏活跃过期场景的收益，均不落地。

落地范围仅为 `engine.withRepeatLimits`：按 `(stage, RepeatLimit)` 合并相同约束的站点，以 `NOT (site IN (...) AND stage = ? AND repeat >= ?)` 代替重复否定条件。保持 SQL 三值逻辑、未注册站点和无上限阶段行为；不同阈值/阶段不能合并。分组每次构造时计算，不缓存；维持单条聚合、Engine context、原锁序、tickerWG/Stop 和原子写路径。

候选两轮中，100k 全达上限由约 204–206ms 降至 162–163ms，读取操作数仍约 100001；收益来自简化剩余条件，不是消除扫描。最终生产矩阵、实库 NULL/混合上限回归及测试/race 证据见 [全达上限成本报告](../reviews/2026-11-14-repeat-cap-cost.md)。不引入运行时查询策略切换、覆盖索引、ICP 配置或缓存；没有共同阶段/阈值的站点不能得到条件压缩收益。

本次 [条件合并复审](../reviews/2026-11-14-repeat-cap-rereview.md) 未发现生产语义缺陷，补齐 TRUE/FALSE/NULL 标量对照、同阈值跨阶段、实际分组 SQL 的取消/排空及负载分布/匹配行数断言。四类错误 overlay 均被预期断言拒绝。新增断言后的两轮交错实测，100k 全达上限由 299.164/302.079ms 降至 260.668/259.558ms（12.9%/14.1%），Handler 仍为 100001；不能推广为无共同约束或冷缓存场景的固定收益。未引入额外优化。
