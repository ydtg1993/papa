## 1. 目标与范围

目标是让账号从“接入、登录、核验、使用、异常缓冲、恢复或隔离”到“任务后续补偿”形成可解释、可操作的流程，减少误判和人工排查。

本轮明确提出的新增需求：

1. 账号不能遇到一次问题就被认定失效，需要缓冲和独立核验。
2. OA 需要添加账号和重新登录的入口，能够承接密码、验证码、扫码和第三方登录等差异。

此前讨论建议一并纳入待办：条件化任务补偿、账号专项指标与告警、后台关联操作、恢复策略动态配置、账号使用预算、备用账号预验证、策略历史与恢复。

沿用已经确定的规则：

- Papa 是单实例通用框架；真实站点登录协议、采集目标、业务模型和站点验收留在独立业务模块。
- 同一任务尝试固定账号及身份快照；发现问题后结束本次尝试，不在任务中换号重跑。
- 账号调度和任务补偿各自负责自己的状态。调度器管理账号，补偿器在条件满足后重投原任务。
- 当前健康账号持续使用，不按请求或任务轮流换号；账号并发已满不视为失效。
- 去重继续沿用页面／既有幂等规则，不加入账号、账号池或浏览器档案维度。
- 已发送请求自然结束，治理主要限制新的操作；不复活 Agent，不增加分布式协调体系。
- 只修改工作区文件，审查与 Git 提交由用户完成。

当前限制已经从代码确认：

- 账号池接到 `Expired`、账号 `Challenge` 或固定出口故障分类后会直接隔离；普通超时、403、站点挑战已有独立处理，不能笼统描述为“任何错误都会换号”。
- `defaultClassify` 当前把完整 HTTP 401 分类为 `Expired`，池请求入口再交给 `ReportFailure` 隔离。因此“单次 401 先核验”涉及现有 `Outcome` 分类契约的演进，不能只增加一个 OA 状态标签，详见 §4.3。
- 已有核验支持手动请求、协调器执行及成功／失败后的状态发布。但 `verifyTransport` 包含 Resume、HTTP ensure 与浏览器 WithBrowser，可能恢复或重新登录，不能直接作为“仅检查可疑原状态”的实现，详见 §4.4。
- `PoolOptions.ReverifyInterval` 是可选能力，默认关闭；现有 OA 没有其完整动态编辑入口。
- 当前账号可用时，池选择逻辑直接返回，没有“维持指定数量近期已验证备用”的策略。
- 错误队列的主要筛选条件是失败状态和补偿代数，没有按失败类别及恢复条件建立完整筛选机制。
- OA 管理的是已注册账号，尚无完整的账号资料新增、登录过程和凭据更新流程。
- 账号身份历史主要依靠可选 Trace；池切换记录保留最近 100 条，不等于永久的账号—任务关联账本。
- 动态策略页面已有来源、生效值、修改预览、冲突保护与草稿保留，不重复列为缺失功能。

## 4. A01：账号异常缓冲

### 4.1 建议规则

采用“可疑状态 + 短暂冷却 + 独立核验”。单纯统计请求失败次数容易把一批并发失败当作多份独立证据，不适合作为唯一判据。

| 信号 | 建议处理 | 能否直接认定账号失效 |
| --- | --- | --- |
| 普通超时、网络错误、5xx、解析失败 | 按任务、网络或站点问题处理 | 否 |
| 整站 429、明确网站挑战 | 使用站点冷却／挑战处理，保留账号状态 | 否 |
| 单次 401、疑似登录页、其他模糊认证异常 | 待核验；暂缓该账号新操作；保留凭据 | 否 |
| 独立检查确认身份仍有效 | 恢复原账号，结束本轮可疑状态 | 不换号 |
| 间隔核验确认当前登录态无效 | 隔离相应登录态，允许调度器选择备用 | 确认会话失效，不自动等同永久封号 |
| 核验超时或网络失败 | 结果未知，退避再查；等待过久告警 | 否，等待超时不能当作失效证据 |
| 可信的明确封禁／撤销结果 | 标明具体原因，停止继续尝试 | 可按站点明确契约处理，不套用普通缓冲 |
| 账号需要人工验证 | 标为待人工处理，停止自动登录轰炸 | 不等同永久失效；与整站挑战区分 |
| 固定代理暂时故障 | 出口不可用、冷却和探测；保留身份凭据 | 否；确认出口持续不可用后的池补偿保留独立原因 |

缓冲期的任务行为：出问题的当前尝试失败，跳过认证类异常的阶段内立即重试，等待后续补偿。新任务在认领前等待账号就绪；同一在途尝试的后续操作受到门控，已经发送的请求自然结束。

### 4.2 必须覆盖的细节

- 核验按站点、账号和凭据版本合并；同一轮并发报错不能瞬间达到独立核验次数阈值。
- 旧响应不推翻新版本已经验证成功的结果；恢复和隔离都检查对应版本。
- 核验首先检查当时使用的状态，不能先隐式重新登录，再把新状态成功误报为旧状态一直有效。
- HTTP 登录态、浏览器登录态、账号封禁、人工验证和固定出口故障分别表达。局部证据不能直接推断其他传输状态失效。
- 冷却结束只允许再次核验；重启不直接清除待核验、停用或人工处理状态。
- 核验使用站点预算，设置超时、退避和运行上限。跨站点核验应避免一个慢站点长期阻塞其他站点调度。
- 恢复账号作为候选，不自动抢回当前健康账号。
- 池任务与显式账号 API 共用必要的暂停／版本约束。显式 `Manager.Do` 现有 GET/HEAD 有限认证恢复契约需要单独检查兼容性，不能让池任务借此绕过失败后补偿规则。

此前讨论的“等待 10 秒、两次间隔核验”仅是示例。正式默认值、时间窗口、检查成功门槛及超出等待预算后的操作，要在详细设计中确定并可配置。

### 4.3 Outcome 分类的演进与兼容

当前实际链路为：[`defaultClassify`](E:/go-project/test_papa/papa/pkg/account/types.go:164) 将 401 返回为 `Expired` → 池请求入口返回 `ErrExpired` 并调用 `ReportFailure` → 隔离和候选切换。`Outcome` 是响应分类，账号“待核验”是管理状态，两者需要明确映射，不能混用。

| 演进方式 | 影响 | 当前建议 |
| --- | --- | --- |
| 新增 `NeedsVerify` 或 `Suspicious` 分类，默认 401 使用新分类；`Expired` 保留确认失效语义 | 可以表达模糊信号和强证据，但需更新所有分类消费入口及兼容测试 | 优先采用；名称尚待定稿，当前代码没有这些常量 |
| 保留现有分类名，把 `Expired` 整体改成疑似失效 | 会改变现有自定义 Classify、显式账号 API 及错误处理对 Expired 的理解 | 不作为默认建议；若采用必须明确迁移语义 |

无论选择哪种方案，都需要覆盖默认分类器、自定义 `Config.Classify`、HTTP 池请求、浏览器捕获／检查、显式账号调用和任务错误分类。`Unknown` 继续表示没有有效结论，不能作为可疑认证状态或登录有效的替代。

对新增分类的建议映射：模糊认证响应进入待核验，受控检查给出“有效／确认无效／未知／需人工”等结果，再由同一个协调器决定恢复、继续缓冲或隔离。`Expired`／`ErrExpired` 只作为确定失效证据的使用边界、旧业务曾将单次 401 返回 Expired 的迁移办法，以及显式 `Manager.Do` GET/HEAD 原有有限恢复行为，须在派发实现任务前定稿，不能静默修改。

### 4.4 与现有 Verify／verifyAccount／verifyTransport 的衔接

实施方向是扩展已有核验体系，复用一个协调器和一套状态发布流程。这里的“独立核验”指核验独立于失败任务执行，不表示新建第二套调度器。

| 现有位置 | 当前职责 | A01 的复用与改造点 |
| --- | --- | --- |
| [`Pools.Verify`](E:/go-project/test_papa/papa/pkg/account/pools.go:306) | 校验管理版本，设置隔离与待验证标志，唤醒协调器 | 保留 OA 提交入口和版本检查；明确核验目的，不能把疑似事件直接转成现有“先隔离”的人工恢复动作 |
| `reconcile`／[`verifyAccount`](E:/go-project/test_papa/papa/pkg/account/pools.go:682) | 执行有界核验，控制并发、超时、站点预算，按版本发布恢复或隔离结果并持久化 | 复用调度、排他和持久化；增加可疑态、间隔核验及模式化结果处理；未知错误不能沿用普通失败即隔离的分支 |
| [`verifyTransport`](E:/go-project/test_papa/papa/pkg/account/pools.go:743) | PinIdentity 后 Resume；HTTP 通过 load／ensure，浏览器通过 WithBrowser；可能登录或刷新 | 在现有传输核验实现中分离“检查现有状态”和“允许恢复登录”两种执行模式，复用底层检查和隔离浏览器能力 |
| `reconcilePool`／选择状态 | 当前成员不可用时查找替补 | 待核验时暂停新的使用但保留当前选择；不能仅因成员暂不可用就提前换号 |

“仅检查现有状态”模式使用触发异常时对应版本的凭据与身份快照，执行受控的 HTTP Check／Browser.Check；不调用可能隐式 Login 的 ensure／WithBrowser 恢复流程，不通过 Resume 自动解除其他暂停原因，不以近期有效缓存代替这次检查。检查期间出现更新版本时，过期核验结果不得发布。

“允许恢复登录”模式承接初始接入、明确重新登录以及隔离后的恢复，继续复用已有 ensure／WithBrowser 等认证能力。检查与恢复共享协调器、版本守卫和操作结果记录；OA 应能区分本次检查原状态成功，还是重新登录后恢复成功。

现有 `verifyAccount` 的重试循环也不能直接当作“间隔独立核验”：需要明确每轮证据、下一次执行时间、未知结果退避，以及成功／确认无效后不同的状态推进。现有 `Pools.Verify` 的兼容行为和内部模式表达放在 §11 定稿，避免实现者只增加一个 Suspicious 前置态，却继续借原路径隐式登录或立即隔离。

## 5. A03—A04：OA 账号接入与多方式登录

### 5.1 账号与池分开管理

“账号管理”负责资料、登录、核验、凭据更新、停用和重新授权；“账号池”继续负责成员、顺序、当前选择和调度。

账号键不使用密码或 Cookie 的哈希生成；更换凭据不改变账号身份。现有代码注册账号继续兼容，新增持久账号使用明确的来源标识和冲突规则，不能覆盖同键的现有注册。

建议流程：选择已接入站点 → 填写资料／选择登录方式 → 完成登录 → 核验真实账号及采集能力 → 保存 → 加入同站账号池。

- 可保存“待登录”草稿，未核验账号不参与采集。
- 核验展示实际识别到的账号、权限范围及 HTTP／浏览器能力；登录成其他账号时阻止误绑定。
- 更新旧账号使用独立候选状态；验证失败不覆盖旧可用凭据，成功后按版本约束发布。
- 新账号加入池不自动替换当前健康账号；不同权限账号继续分池。
- 已接入站点的常规新增账号应能运行时生效并在重启后恢复；新增站点登录协议仍属于业务开发。

### 5.2 A04a 登录适配与 A04b 登录态导入

A04a 负责站点适配器及可暂停、可继续的登录过程，包含密码、结构化验证码输入和扫码状态等；A04b 负责站点声明格式的登录态导入、校验与发布。二者可以共享账号和候选凭据接口，均不以远程画面控制为前置条件。需要人在网站页面上操作的登录方式交由 A04c，不能用通用验证码输入框承诺解决任意交互挑战。

| 方式 | OA 交互 | 站点业务职责 |
| --- | --- | --- |
| 用户名／密码 | 输入所需字段，发起登录 | 登录接口或页面步骤、真实身份检查 |
| 短信／邮箱验证码 | 发起、等待输入、提交、超时与重新发送 | 验证码协议及发送限制 |
| 密码加二次验证 | 自动步骤后进入待人工输入 | 验证步骤及完成判定 |
| 扫码 | 展示二维码、有效期和结果 | 获取二维码、轮询状态、识别账号 |
| 浏览器人工登录 | 在受控浏览器内完成复杂步骤 | 登录页面、允许流程及回站检查 |
| 第三方登录 | 承接网站原有流程或已配置的正式授权接口 | 跳转与身份检查；正式 OAuth 接入需要相应客户端条件 |
| 导入 Cookie／Token | 按站点声明的格式导入并核验 | 凭据格式、适用范围、有效性和账号识别 |

OA 只显示站点适配器声明支持的方式，不承诺通用表单自动识别任意网站。第三方登录不默认意味着 Papa 可以直接申请或使用该网站的 OAuth 授权接口。

框架提供登录过程的创建、等待输入、继续、取消、超时、结果与资源回收；业务提供字段定义、开始／继续步骤、成功检查、账号识别和可否自动刷新的能力声明。这些是建议职责，不是已经存在的新 API。

登录过程有独立 ID、有效期和单次输入约束；重复提交、过期验证码、刷新 OA、重复取消、进程重启都必须有明确结果。登录不占采集任务执行名额，但仍受浏览器资源和站点请求预算约束，并限制同时进行的人工登录数量。

### 5.3 A04c：独立的远程浏览器交互子系统

服务器部署时，Rod 页面在服务器；用户本地浏览器登录态不会自动传到服务器。

A04c 是独立的大工作包，不能作为密码／验证码适配的附带 UI 功能估算。受控远程浏览器交互与 A04b 结构化登录态导入是两条不同路线：导入完成只说明可验证并使用已有状态，不表示具备远程登录能力；远程交互也不保证任意网站状态都可脱离原环境移植。

该子系统需单独设计、估算和验收以下范围：

| 子能力 | 需要交付的内容 |
| --- | --- |
| 控制与传输 | 服务端持有 Rod／CDP 控制权，通过受控 WebSocket 或选定传输发送画面及操作；避免裸露可任意控制浏览器的调试端口 |
| 画面渲染 | 前端展示远端页面，处理尺寸、缩放、帧率、带宽和慢连接；画面传输方案需技术验证 |
| 人工输入 | 键鼠事件、焦点、坐标映射及必要输入法支持；操作只作用于当前授权登录过程 |
| 页面生命周期 | 登录跳转、必要弹窗／标签页、完成后的身份检查和浏览器上下文归属 |
| 连接权限 | OA 身份与登录过程绑定、连接有效期、并发控制者规则、退出与撤权 |
| 断线与回收 | 有界断线宽限、重连身份检查、会话超时、取消、资源释放与进程重启后的终止结果 |
| 资源与观测 | 单实例并发登录上限、浏览器预算、交互错误反馈和脱敏审计 |

现有 Rod 回调不代表这些能力已经具备。规模应作为可与 A01+A02 相比较的独立子系统审视；本报告不在缺少技术验证和任务拆解时给出等工时结论，也不把它计入普通表单适配的估算。A04c 先完成单独的技术验证与设计，再派发实现任务。

登录沿用账号计划绑定的档案和固定出口。允许的登录跳转与最终采集认证范围分开管理；结束后检查实际目标站登录态。现有状态快照有 Cookie、LocalStorage 等覆盖边界，不能默认承诺任意跨域 SSO、IndexedDB 或设备绑定凭据都可导入恢复。

验证码仅用于本次登录；密码、Cookie、Token 使用专门凭据存储，不放入普通策略、任务 Meta、日志或可回放截图。是否保存密码由登录方式和用户选择决定；需要以后自动提交的密码使用可解密的专用加密存储，不能将账号索引哈希误当作凭据存储方案。

## 6. A02、A05—A07：补偿与运维闭环

### 6.1 条件化补偿

在现有错误队列上增加可持久表达的失败类别、补偿条件、最早执行时间、人工处理原因及尝试关联。具体列名与存储拆分在详细设计中确定。

| 类别 | 补偿条件 |
| --- | --- |
| 账号待核验／失效 | 原池已经可用，且任务允许使用该池的替补账号 |
| 临时网络问题 | 达到退避时间及补偿上限要求 |
| 站点冷却 | 同时满足任务排期和服务端完整等待期限 |
| 人工验证 | 明确的人工解除及后续核验条件满足 |
| 解析不匹配 | 有限自动补偿，之后提示检查业务规则 |
| 永久不存在／业务终止 | 由业务明确声明终止条件，不无限重投 |

补偿器只读取账号就绪条件，不直接登录或换号；账号调度器不负责重投任务。依赖未就绪时显示等待原因，避免反复投递、反复消耗补偿代数。原任务、去重键和池归属保持不变；人工重投、错误队列、轮询与启动恢复路径要共同遵守互斥及新补偿约束，防止从其他入口绕过。

### 6.2 专项事件、指标与告警

复用现有事件／通知通道，增加账号待核验、核验结论、池耗尽、备用不足、连续登录失败、等待超时和恢复事件。任务在认领前等待时也能产生池级告警，不依赖任务终态失败。

指标至少覆盖可用与待核验账号数、近期核验结果、等待任务数及最长等待时间、切换次数、登录频率。通知按站点和账号池去重、节流，恢复后发送恢复结果，避免每个失败请求重复告警。

### 6.3 OA 操作链路

目标：异常账号 → 原因与核验结果 → 关联任务 → 登录／验证处理 → 可补偿任务预览 → 执行补偿 → 查看结果。

- 验证操作有可查询的进度和最终结果，不能只提示“稍后刷新”。
- 展示待核验原因、下一次检查时间、有效配置来源和当前限制。
- 切换历史中的触发任务可跳转；支持按站点、池、账号、时间和原因关联排查。
- 对“受影响任务”的统计注明覆盖范围。补齐必要的有界持久关联，不能假定 Trace 永远开启或永久保留。
- 补偿前展示可执行、仍需等待、需人工处理的数量与原因；执行后保留逐项结果。
- 批量停用／验证等操作保留版本检查与部分失败反馈；密码和验证码不回显。

### 6.4 恢复策略动态配置

将缓冲时间、核验间隔、确认门槛、超时、退避及人工处理规则纳入可校验策略；将现有可选复验能力接入 OA。账号并发等当前注册时固化的参数，只有完成运行时更新契约后才标记为可动态修改。

池可以覆盖成员选择和备用目标；同账号跨池的健康判定、额度与凭据政策必须按账号统一，不能因不同池配置互相矛盾。保存预览要展示会影响哪些池和新操作，保留现有配置来源、版本冲突和草稿保护能力。

| 项目 | 待做内容 | 必须守住的语义 |
| --- | --- | --- |

| 场景 | 必须观察到的结果 |
| --- | --- |
| 一次普通超时、403、5xx、解析失败 | 不误判账号失效，不无故换号 |
| 默认 401、自定义 Classify 和显式账号 API | 默认 401 按定稿契约进入可疑核验；确认失效分类和旧 API 的迁移／兼容行为有独立回归，不能落入未知分类错误 |
| 可疑账号进入现有核验协调器 | 只产生一轮受控检查；仅检查模式不调用 Login、不偷偷 Resume，也不使用检查缓存掩盖当前异常 |
| 仅检查无效与核验网络错误 | 前者按证据阈值推进，后者保持未知并退避；不沿用通用失败立即隔离；核验间隔真实生效 |
| OA 请求检查与请求恢复登录 | 共用协调器、版本守卫和结果记录，明确显示实际执行方式；不会产生第二套调度或并发相互覆盖 |
| 疑似认证失败后检查成功 | 原账号恢复，无新页面任务、无中途换身份 |
| 同一凭据版本并发多次失败 | 合并核验，不用请求数量冒充独立证据次数 |
| 新版本成功后收到旧失败响应 | 不撤销新状态 |
| 核验网络持续异常 | 显示未知、退避与告警，不能伪造失效结论 |
| 固定出口故障 | 出口状态与账号／会话状态分开，凭据不因故障被无条件清空 |
| 账号恢复或调度换号 | 失败任务仍由补偿器处理，去重与原池归属保持 |
| 重启发生于待核验／登录／补偿期间 | 恢复持久状态，临时登录明确终止或恢复，不带过期交互继续执行 |
| 添加新账号或更新旧账号失败 | 草稿不可采集，旧可用凭据不被替换，不覆盖其他来源同键账号 |
| 登录返回另一个真实账号 | 阻止误绑定，显示脱敏身份核对结果 |
| 验证码重发、重复提交、过期提交、取消 | 状态一致，输入不会用于其他登录过程 |
| 人工登录断线或超时 | 回收浏览器及交互资源，不遗留可继续控制的入口 |
| A04b 结构化导入独立部署 | 不依赖远程画面／键鼠通道即可核验支持的状态格式，也不会把导入成功标成支持人工远程登录 |
| A04c 画面缩放、跳转、弹窗及慢连接 | 显示与输入映射正确；操作不串登录过程；有界资源消耗且能明确结束登录 |
| A04c 连接到期、撤权或其他用户尝试重连 | 拒绝继续控制；不会暴露原始浏览器调试入口；回收策略与登录状态一致 |
| 无账号可用、依赖仍未恢复 | 不占全局任务执行许可，不反复消耗补偿代数，可查询等待原因 |
| 人工重投与自动队列同时操作 | 同一原任务不会并发执行两份，不能越过新补偿约束 |
| 同账号跨池使用预算 | 统一计量、原子扣减，配额等待不导致换号 |
| OA 两个页面并发保存或回执丢失 | 版本冲突和结果核对有效，不自动重放敏感操作 |
| 策略恢复历史设置 | 生成新版本，不覆盖当前无关变更，不倒退运行状态 |

验证层次：纯状态机与版本并发测试、真实 MySQL 持久化／重启测试、本地合成 HTTP 与真实 Chromium 登录测试、OA 交互测试、涉及脚手架时的生成项目构建。真实站点登录与业务查询验收放在对应业务模块。假库不能替代数据库迁移和并发更新语义验证。
