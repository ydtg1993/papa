## 1. 总体判断

Papa 已是具备任务持久化、并发执行、治理、账号与浏览器资源管理、后台运维和观测报告的 **Go 单实例模块化爬虫框架**。它的主要问题已从目录归属不明转向跨组件行为的一致性：单任务资源能否受控、文件产物是否安全发布、跨轮次证据是否仍能准确还原、取消是否真正终止后续工作。

初次诊断确认 9 项问题：1 项 P1、8 项 P2。下载器代理超时污染、分片合并破坏旧产物和 3 项报告问题已有运行复现；其余 4 项当时由源码直接推导，没有用危险的 OOM 实验或真实业务数据验证。九项现已修复并经全仓回归、定向复审及 Trace 实库补验；这一闭环不等于“生产无风险”。

现有架构有实质解耦：App 管装配与关停协调，Engine 内部组件分别拥有提交、调度、执行、熔断和证据；admin/server 是组合入口，HTTP/前端资源归功能模块。继续机械增加子包不是当前最高优先事项。

## 5. 架构与状态诊断

### 已成立的边界

根包不另建运行状态；core 是值与协议；taskstore 管 SQL 状态谓词；execution 管未确认持久化；scheduler 管调度容器；runtimecontrol 管策略版本与不确定写入；sitedecl 管声明复制和计划。admin 功能包通过服务接口接入，obs 不反向控制 Engine。依赖守卫有助于阻止回退，但无法证明锁序和 SQL 原子性。

App 的 `shutdownRun` 对 HTTP、Engine、业务回调、账号/诊断和消息监听分别取得排空结果，再决定是否关闭共享 DB/浏览器。它保留了“不以取消冒充完成”的关键原则。HTTP handler 返回后自行启动的业务 goroutine 必须通过宿主生命周期登记，不能靠请求追踪器自动发现。

### 仍然存在的设计限制

1. **不是进程硬资源沙箱。** R1–R7 已增加有限驻留、输入额度、共享下载令牌和流式读取；Task 可变载荷、多个独立报告调用、业务 Section/Fetcher、外部 FFmpeg 与成功产物保留仍需容量规划和系统配额。
2. **没有统一硬关停时限。** 多阶段等待各用自己的预算；最新在线 obs 的转发、报告及归档已共享最多 2 秒等待，不再等待任意离线分析，且不借用业务 DB。审计、代理或业务回调和外部 I/O 是否合作取消仍影响整应用结束时间，不能把 obs 的预算外推为整个 App 的硬退出保证。
3. **关停观测有范围限制。** `run_stopped.outcome` 只代表 Engine 的 drained；App 最终还有其他排空条件。`internal/app/bootstrap.go:185`、`lifecycle.go:90`，不能据一条 drained 事件判断整应用已释放所有资源。
4. **部分启动失败只记录日志。** `internal/app/http.go` 中 ListenAndServe 失败记录错误，未反向结束 Run。采集可继续但后台不可用；需由产品约定后台是否必需，再决定是否改为启动失败。这不是本轮已证明的数据损坏。
5. **证据完整性弱于执行状态完整性。** 任务状态有版本和条件写入，归档/Trace 已按执行 UUID 隔离，但写入仍是尽力观测，失败可丢证据；v4 不读取旧 SQL Trace，文件查询不是任务状态事务快照。事件允许丢弃，报告四文件不是整组事务。故障诊断不能把观测层当唯一事实源。
