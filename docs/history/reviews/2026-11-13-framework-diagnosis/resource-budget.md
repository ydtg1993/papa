## 结论与口径

初诊时存在缺少本地硬上限的增长路径，不能由有界 worker、时间窗口或轮转保留期推导出进程内存有界。最突出的是 spill/delay 常驻任务、报告事件及单行输入、M3U8 播放列表和响应体；续传索引则同时存在内存、磁盘与全量检查点写放大。

本文“无界”指没有独立于输入规模的本地容量约束，不表示某个有限任务永远增长或已经在生产复现 OOM。网络授权限制访问目标，不限制被授权源的内容规模。以下严重程度是修复优先级，不是攻击可达性评级。

已有保护必须保留：worker 队列及高水位、下载固定 worker、输出路径锁、任务 CAS、取消准入与在途排空、event emitter 有界丢弃队列、日志索引默认 20000 条/每签名 3 个样例、M3U8 单行 1 MiB 限制。下载 labor 引用归零会删除，并非历史任务永久缓存；delay Pop 清零引用，但底层切片仍可能保留高水位容量。

### 相邻的放大因素

- filedown 失败/取消保留分片用于恢复，m3u8 保留模式也有意留文件；缺少统一临时目录配额、空闲过期回收和活动文件保护协议。正确的可恢复行为可能积累磁盘占用，不能直接按年龄删除仍被使用的文件。
- 两下载器的 proxyTransports 按不同代理地址缓存且不清理；这不是本轮优先主线，但长期动态代理集合需要独立容量/空闲回收设计。不能在请求仍使用 transport 时随意破坏复用策略。
- 单任务限额不等于单进程限额。多个阶段、多个下载实例和报告并行时，需要共享准入令牌；仅依靠 Engine worker 数也覆盖不了库的独立使用者。
- 日志/事件源轮转可以减少常见输入规模，但导入日志、压缩膨胀、窗口内高事件率及配置放宽仍绕过这一间接限制。报告产物 retention 不限制源事件读取。

## 改进路径比较

| 路径 | 收益 | 代价/风险 | 建议 |
| --- | --- | --- | --- |
| 只加计数/文件硬限额，超限统一报错 | 最快阻止单输入失控，容易回归 | spill 已接受的持久任务不能直接报错丢责任；全量读取和检查点写放大仍在 | 用于输入边界止血，不能作为完整队列方案 |
| 有界内存工作集 + 数据库待执行扫描；有预算的流式输入 + 兼容适配 | 利用已有持久任务和 not_before，内存只保留近期可执行工作；按责任包逐步落地 | 要证明内存未驻留任务在当前进程仍能被发现，处理轮次/优先级/公平性和旧 API | **推荐主线**，先输入限额，再队列容量与持续补充 |
| 立即统一磁盘队列/外部排序/所有插件增量协议 | 可处理更大输入，资源控制更完整 | 新增磁盘生命周期及格式兼容成本，改动面大 | 仅在量测证明需要时引入；不扩展为分布式系统 |

## 推荐方案与职责合同

### 1. 有界调度工作集：Engine + scheduler + taskstore

- scheduler 只拥有容量、成员索引、分批取出/归还、唤醒和公平选择；不持有 Engine、不访问 DB。spill 可先收紧同包组件，不因文件名机械抽包。
- Engine 拥有提交与“谁负责继续发现该任务”的协议。持久任务已提交成功后，内存满应保留 durable pending，由**持续**补充扫描负责，不能只依赖下一次启动恢复或用户开启的 RecoverQueue。非持久工作不能无声丢弃，必须明确拒绝并返回可识别超限结果。
- taskstore 拥有 pending/due/版本条件和按库时间的分页查询。远期任务留数据库，只将近到期窗口和有限条目放 delay；启动、恢复和批量提交都走同一容量协议，不能一次恢复全部积压。
- 内存成员需要覆盖池内、spill、delay、已取出的回灌批次；索引键和状态转换必须区分当前轮次，不能永久按任务 ID 去重导致合法重跑失踪。Take 后的 detached 项仍计入预算，Restore 不重新占一份令牌；释放必须 exactly-once。
- 全局上限约束总量，站点/阶段配额保证一个暂停站不占满全部容量；回灌按小批量/时间片轮转，队满及时停止本桶，保留公平性和加急语义。
- 禁止在 breakerMu、pauseMu、spill/heap 锁内等待容量或执行 SQL；继续保持 breakers.breakerMu → pauseMu → (overflow.mu | e.mu) 的既有锁序。worker 内提交子任务不得阻塞等待由同一池 worker 释放的空间，否则会自锁。
- 每批和单条读取前检查 context，查询传 context；取消后还未处理的批次必须归还或保留 durable discoverable 状态。已确认条件更新后的任务继续有归属，不以取消撤销持久化事实；停止仍等待在途操作，不能提前关闭共享资源。

建议量测参数（尚未决定默认值）：全局/站点/阶段驻留数、驻留负载估算字节、单次回灌批量/时间片、delay 预取时间窗口。Task 字符串和 Meta 大小不固定，只有“条数”不能形成严格字节保证；需同时限制输入负载或使用轻量持久引用。

### 2. 报告输入预算：obs 子包负责，reportrunner 只编排

- eventlog 新增带 context/预算的读取入口：文件数量、单行字节、累计**解压后**字节、事件数/估算驻留量；限制必须在 ReadAll/ReadString/Unmarshal 放大前生效。时间/run 筛选尽可能前移，但仍需保留坏行、重复、缺口统计的原口径。
- LoadDailySources 的兼容入口保留；新增逐日消费接口供 CLI/runner 使用，消费一日后释放。先消除所有日 Sources 同时驻留，再通过有配额的临时分桶或时间索引降低反复扫描；不得假定导入文件按时间排序或在遇到窗口外事件时直接停止。
- 精确去重键本身也需要预算，不能把 Events 流式化后留下无界 seen。短期超限显式终止；长窗口需精确外排/磁盘去重时，必须同时设置磁盘配额和清理责任，不能悄悄用近似去重改变指标。
- logidx 保留现有条数和样例限制，增加输入行/字节/context 约束；对窗口外和坏行也计扫描预算。
- 报告超预算不得给出完整验收“通过”。优先保留旧产物并返回可识别资源错误；若产品明确允许部分报告，必须展示 incomplete/truncated、覆盖范围和 unknown 结论，不把截断样本当总体统计。
- obs.Section/Pattern 目前可拿全量事件，自定义插件不能直接改为增量而宣称兼容。先为原接口提供有预算的完整输入，再引入可选流式扩展协议。runner 只负责配置、生成串行准入及取消排空；App 不实现解码/去重。

### 3. 续传状态：各下载包拥有格式和检查点

- 先设 MaxResumeBytes、MaxChunks/MaxSegments、输出/临时磁盘预算；从 HEAD 推导 N 后在建立索引前校验，读旧状态按字节和条目双重限制。超限返回明确错误，旧目标/状态/分片不被误删；不要把资源限额错误当“损坏状态”自动从头下载。
- 版本化续传格式：考虑位图/区间表示完成集合、按索引生成路径替代重复存字符串；旧 JSON 仍可有界导入，迁移采用临时文件完整写入后替换。连续区间压缩最坏也可能 O(N)，需要保留硬片数上限。
- 专用检查点所有者合并完成事件，按时间/变更量写快照或增量日志，避免 worker 在 resumeMu 下承担整份序列化/磁盘 I/O；有界事件队列不能丢完成事实，可从完整分片重新验证恢复。快照代次必须防止旧快照覆盖新状态，结束前 flush 并等待写者退出。
- 不应为每片增加 goroutine；取消后等待已准入请求/回调和检查点收尾，保持输出锁和原发布协议。临时数据 GC 只处理无活动引用且符合明确过期策略的任务，不能仅看 mtime。

### 4. 播放列表和分片：m3u8 按内容角色实施预算

- 分别设置 playlist 字节、片数、单个 key/init/media 字节和同时在途字节预算；有效上限取本地预算与可信长度约束较小值，没有 Content-Length 时同样适用。输出 playlist 模式也须受总字节限制。
- 边读边检查并写临时文件；非加密分片优先流式落盘，限速放到读取循环。AES-CBC 流式化要保留块边界、最后一块 padding 检验与失败不发布；先做有界全量解密也可作为小步方案。
- 分片总数在 append 之前检查；超限整项失败，不能拿播放列表前缀去合并并返回成功。多个下载实例可注入共享字节预算组件，组件只拥有令牌，不引用 App/Engine；独立使用下载包也有明确的本地保护。
- 减少内存不能把风险全部转移到磁盘，临时写入必须纳入磁盘配额；失败保留与自动回收策略需明确区分。

## 实施顺序与验收

1. **输入边界先行**：R4/R6/R7 的行、解压字节、状态大小、片数和响应体上限；明确超限错误和旧数据兼容。参数名仅为方案，当前配置尚不存在；默认值应基于合成负载和实际部署预算确定，不能凭空承诺适合全部业务。
2. **缩短不可取消区间**：报告读取传 context、spill 分批回灌和剩余项归还；验证 Stop 不提前返回、失败仍可恢复。
3. **调度工作集有界**：先完成持久 pending 持续发现与完整成员/令牌所有权，再启用 spill/delay 硬容量，防止只加 cap 导致任务停滞。按需要迁移查询索引，使用隔离 MySQL 验证 CAS、NotBefore、重复投递与重启。
4. **降低持续成本**：续传检查点增量化、报告逐日消费/分桶、媒体流式落盘；最后量测并确定合理默认值。

必须补的验证：

- 暂停站持续提交、一个 worker 递归提交子任务、池满与回收并发、延迟远期积压、重复同 ID 不同轮次；确认驻留上限、持续公平恢复、无丢任务/死锁，并覆盖取消在预留/持久化/发布每个边界。
- 大小恰好限额与超一字节、chunked、压缩高膨胀、超长坏行、大量窗口外数据、多个日/run 交错；小输入与旧报告逐字段一致，超限不产生假通过。
- 旧 JSON 恢复、重复/非法索引、稀疏完成、检查点失败与乱序完成、取消/重启、已有产物保护；用小 fixture 验证逻辑，不执行危险 OOM。
- 超多短播放列表行、巨型 Content-Length、无长度分片、加密段 padding 错误、并发多实例；监测峰值在途字节、临时磁盘、最大 worker，而不是只测完成吞吐。
- 最终压力指标：heap/RSS 高水位、队列和 detached 数量、预算等待/拒绝、最老 pending/due 延迟、扫描/解压字节、检查点写字节与耗时、DB 查询率、Stop 排空时间。GOMEMLIMIT 可辅助 GC，不替代准入预算和 RSS 验收。

## 本次验证与范围

本次是源码和已有测试审查，未修改生产行为，未做 OOM、生产数据扫描或长稳压力试验。运行 `go test ./engine/internal/scheduler ./obs/eventlog ./obs/logidx ./obs ./internal/reportrunner ./pkg/middleware/filedown ./pkg/middleware/m3u8 -count=1 -json`：7 包通过，296 个测试/子测试通过、3 个跳过。日志 `.review-tmp/resource-budget/tests.jsonl`。已有测试通过说明现有语义回归稳定，不证明本文提出的预算已实现或峰值有界。
