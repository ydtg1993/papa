# Papa 启动恢复手册

恢复任务保留数据库中的 `not_before`；普通尚未到期的任务保留持久 pending，由到期唤醒补充，不因恢复加急提前执行。投递延迟不重新计算，最终认领再次检查数据库 UTC 时间。详见 [任务时间与持久化延迟](TASK_TIMING.md)。

> 面向：进程崩溃 / 重启后，怎么把停在 `pending` / `processing` 的任务捡回来继续跑。
> 配套：[ERROR_QUEUE.md](ERROR_QUEUE.md)（失败任务重试，两者按状态分工）。

---

## 0. 一句话

进程在抓取中途挂了，会留下一批停在 `pending`（已入库未入队）或 `processing`（取走了但没处理完）的任务。
单实例启动时，在任何入口提交和 worker 认领之前，同步把遗留的 `processing` 重置为 `pending`。此时没有本进程正在执行的任务，不需要按更新时间猜测孤儿；重置失败会阻止启动。运行期不再重置 processing，只补充 pending。

恢复始终启用：启动时重置上次进程遗留、且不由可靠结算 journal 拥有的 processing，运行期持续按阶段空位补充 pending。任务提交、消费释放容量、阶段恢复和到期事件会唤醒补充；有界 channel 与驻留预算控制内存，不使用独立溢出表、定时 drain 或批间暂停。

运行期的认领与终态数据库错误由当前 worker 退避重试，只重试状态操作，不重放已经完成的业务。持续故障遇到取消，或认领可能已提交但回执不明确时，任务会保留为关停未完成项，不谎报成功；重启后仍按本手册的状态与启动顺序恢复。当前协议没有跨进程租约，不能把不明确的认领当成已获得执行权。若业务已经生效、终态尚未落库就崩溃，恢复可能再次执行业务，因此业务写入仍须幂等。

## 1. 配置

写在 `configs/config.yaml` 的全局段（**不再按站点拆**）：

```yaml
recover_queue:
  batch_size: 100             # 每批查询上限；0 = 默认 1000，不能为负
```

仅保留 `batch_size`。实际查询和补位受阶段可用容量约束，满载时 pending 留在任务表；取消时停止补充。旧 `enabled`、`worker_count`、`batch_pause` 已删除，配置这些键会拒绝启动。

## 2. 为什么不按超时判「卡死」

启动恢复依据进程边界，不按 `updated_at < now - timeout` 猜测任务是否中断：

| 毛病 | 说明 |
| --- | --- |
| **漏** | 崩溃前几分钟认领的任务同样需要恢复，按固定超时窗口筛选会遗漏这些 processing 孤儿 |
| **误伤** | 真跑得久的任务（下整部剧、大文件）过了 `timeout` 就被当成卡死重投，**与仍在跑的 worker 撞车写同一份业务结果** |

「意外中断」在启动这一刻是**确定**的，不需要靠时间推测。运行期真正的卡死应该靠给外部调用设超时解决
（`htmlfetch` 与 `rod` 都有自己的 timeout），不是靠事后扫库。

## 3. 判定与重投

启动重置条件为 `status = processing`，在入口和 worker 启动之前执行；原 pending 保持原状态。随后阶段投递器只选择满足时间和补偿条件的 pending。

- `pending` 也会纳入启动扫描：它们可能因驻留预算留在 DB，或入库后尚未入队。持续补充扫描已注册阶段的可执行 pending；processing 孤儿只在启动时按进程边界重置。
- 重投从持久记录还原后走内部恢复入口，`Repeatable` / `Meta` 照抄行上的值；保留已有 `repeat`，不因恢复新增轮次。可轮询 pending 行尚为 0 时，在成功认领时初始化为 1；
  `Urgent` 保留持久记录中的优先级；恢复本身不更改优先级，成功认领时清零。
  其中 `Meta`（业务键，见 [FETCHER_WRITING_GUIDE.md](../guides/FETCHER_WRITING_GUIDE.md) 1.2）是要害：
  它是 handler 认业务行的依据，恢复出来的任务要是没带上，任务会以「结构错误」永久失败 ——
  而这类失败通常不可重试，人工点「重投」也走同一条路。
- processing 孤儿在启动阶段同步重置，保留原轮次、预算与补偿字段；原本 pending 的行省略这次重置，交给 worker 的 `pending → processing` 认领条件最终确认。即使重复排队，也只有一份能认领成功，另一份影响 0 行后跳过。
- 未注册阶段不参与扫描，保留原行。投递等待和池回收不改写状态；读库失败退避后重试。

## 4. 触发方式

启动时自动恢复孤儿；运行期通过事件持续补充 pending，不能关闭。

`engine.ProcessRecoverQueue()` 仅唤醒 pending 补充，不在运行期重置 processing，也不返回完成处理计数。后台不提供额外恢复按钮；任务提交、容量释放、暂停恢复和到期事件自动协调补位。

## 5. 与 error_queue 的分工

| 机制 | 目标状态 | 什么时候跑 |
| --- | --- | --- |
| `recover_queue` | `pending` / `processing` | 启动重置 processing；运行期持续补充 pending |
| `error_queue` | `failed` | 按 `interval` 周期 + 手动触发 |

一个任务同一时刻只属于其中一种状态，两者不会重叠处理。

## 6. 分页游标

恢复是分页扫的（`batch_size`），游标是**自己的 `id`**（keyset），不是 OFFSET。

每阶段保留自己的 ID 游标，按 keyset 读取有限批次。游标、合并唤醒与已投递任务的所有权由投递协调器拥有；尚未认领的任务仍可能保持 pending，不能把每次重复扫描同一批当作进度。

### 关停期间的批处理

Engine 取消后不再开始新批次或领取同批后续任务，查询和条件重置使用生命周期 context。已经成功重置的任务保留为持久 pending，按容量进入有界 channel，批处理等待已准入回调返回后才退出。取消不会把尚未处理的记录标成失败；手动触发仅发送唤醒通知，不同步统计执行完成数。

启动恢复先核对可靠结算 journal。journal 拥有的是任务的精确执行代次，不能只按 task ID 排除，也不能将其覆盖的 processing 行提前重置成 pending；同一任务其他代次仍按持久条件恢复。这样重启时先补终态，不因旧的 processing 恢复路径重放已完成的业务。
